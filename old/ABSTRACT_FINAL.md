## บทคัดย่อ

ปัจจุบันผู้บริโภคให้ความสำคัญกับความปลอดภัยของส่วนผสมในผลิตภัณฑ์เครื่องสำอางมากขึ้น เนื่องจากสารเคมีบางชนิดอาจก่อให้เกิดการระคายเคืองหรืออาการแพ้ต่อผิวหนัง อย่างไรก็ตาม รายชื่อส่วนผสมบนฉลากผลิตภัณฑ์มักพิมพ์ด้วยตัวอักษรขนาดเล็กและประกอบด้วยชื่อสารเคมีที่มีความซับซ้อน ทำให้ผู้ใช้ทั่วไปตรวจสอบข้อมูลได้ยาก โครงงานนี้จึงพัฒนาระบบต้นแบบสำหรับดึงข้อมูลส่วนผสมของเครื่องสำอางจากภาพฉลากผลิตภัณฑ์ด้วยเทคนิค OCR โดยใช้ PaddleOCR (PP-OCRv6_medium) เป็นเครื่องมือรู้จำข้อความหลัก

งานวิจัยนี้ดำเนินการวินิจฉัยและปรับแต่ง pipeline OCR เชิงประจักษ์เป็นลำดับขั้น แทนการเปรียบเทียบเทคนิค image preprocessing แบบดั้งเดิมจำนวนมาก โดยเปิดใช้งานฟีเจอร์แก้ไขความโค้งของภาพเอกสารและฟีเจอร์ตรวจจับทิศทางบรรทัดข้อความในตัวของโมเดลซึ่งเดิมถูกปิดไว้ ร่วมกับการเพิ่มขอบภาพสีขาว 25% รอบภาพก่อนเข้าสู่ขั้นตอน OCR การเพิ่มคำศัพท์ที่ขาดหายไปในฐานข้อมูล INCI ที่คัดสรรมาเฉพาะ และการปรับลด threshold การยอมรับกล่องข้อความของโมดูลตรวจจับข้อความ พบว่าทั้งหมดนี้ให้ผลดีขึ้นอย่างมีนัยสำคัญ โดยไม่ต้องอาศัยเทคนิค preprocessing เชิงภาพแบบดั้งเดิมเลย ใช้เทคนิค Fuzzy String Matching เทียบกับฐานข้อมูลชื่อสารเครื่องสำอาง (INCI) เพื่อแก้ไขคำที่ OCR อ่านผิดพลาดเป็นขั้นตอนสุดท้าย

ผลการทดลองบนภาพฉลากเครื่องสำอางจริงจำนวน 216 ภาพ พบว่าการแก้ไขการตั้งค่า pipeline หลักสี่จุด ได้แก่ บัค mkldnn การตั้งค่า engine settings ฐานข้อมูลคำศัพท์ และการแก้ไขข้อความหลัง OCR ทำให้ค่าตัวชี้วัดระดับชื่อสาร Set F1 ดีขึ้นจาก 0.39 เป็น 0.55 คิดเป็นการเพิ่มขึ้น 41% และการปรับลด threshold การตรวจจับข้อความเพิ่มเติมจาก 0.45 เป็น 0.30 ทำให้ Set F1 ดีขึ้นอีกเป็น 0.57 พร้อมค่า Character Error Rate (CER) ลดลงจาก 0.32 เหลือ 0.26 คอขวดหลักที่เหลืออยู่คือค่า Recall ของโมดูลตรวจจับข้อความ ซึ่งประมาณ 62.7% ของชื่อสารที่พลาดเกิดจากโมดูลตรวจจับมองไม่เห็นข้อความเลย ไม่ใช่ปัญหาการแก้ไขข้อความหลัง OCR อีกต่อไป งานต่อไปจึงควรทดลองแนวทาง เช่น การปรับปรุงคุณภาพภาพต้นทางหรือการปรับแต่งโมเดลเฉพาะทาง ก่อนสรุปประสิทธิผล การ validate เพิ่มเติมบนภาพจำลองสภาพแวดล้อม 4 แบบ ได้แก่ blur, indoor, low_light และ night สภาพแวดล้อมละ 216 ภาพ พบว่าผลลัพธ์ข้างต้นใช้ได้กับภาพคุณภาพระดับปกติถึงแสงน้อยปานกลางเท่านั้น ส่วนภาพเบลอและภาพแสงน้อยมากทำให้ Set F1 ลดลงเหลือประมาณ 0.14 ซึ่งเป็นข้อจำกัดสำคัญก่อนนำระบบไปใช้งานจริง

**คำสำคัญ:** Optical Character Recognition, ส่วนผสมเครื่องสำอาง, การดึงข้อมูลจากฉลากผลิตภัณฑ์, การตรวจจับข้อความ, การจับคู่ข้อความแบบคลุมเครือ

## Abstract (English)

Consumers are increasingly concerned about the safety of cosmetic ingredients, as certain chemicals may cause skin irritation or allergic reactions. However, ingredient lists on product labels are often printed in small fonts with complex chemical names, making them difficult for general users to verify. This project develops a prototype OCR system for extracting cosmetic ingredient information from product label images, using PaddleOCR (PP-OCRv6_medium) as the primary recognition engine.

Rather than comparing a large battery of classical image-preprocessing techniques, this work follows an empirical, staged OCR-pipeline diagnosis-and-repair approach. The engine's document-unwarping and textline-orientation features had been disabled in an earlier configuration; re-enabling them, combined with a 25% white border padding added around each image before OCR, a curated vocabulary patch filling gaps in the reference INCI ingredient database, and lowering the text-detection module's box-acceptance threshold, produced substantial accuracy gains without any classical image-preprocessing step. Fuzzy string matching against the INCI database was retained as a post-OCR correction step.

On 216 real cosmetic label images, fixing the core pipeline configuration (mkldnn crash workaround, correct engine settings, vocabulary gaps, post-processing bugs) raised the ingredient-level Set F1-score from 0.39 to 0.55 (+41%). A subsequent detection-threshold adjustment (box_thresh 0.45 → 0.30) raised Set F1 further to 0.57 and reduced Character Error Rate (CER) from 0.32 to 0.26. The main remaining bottleneck is detector recall: roughly 62.7% of missed ingredient tokens are caused by the text detector failing to locate the text region at all, rather than by post-processing errors. Future work should test approaches such as improved source-image quality and domain-specific model fine-tuning before drawing conclusions about their effectiveness. Follow-up validation on four simulated environmental scenarios (blur, indoor, low_light, night — 216 images each) shows these gains hold only for normal-to-moderately-dim lighting: blurred and very-low-light images cause Set F1 to collapse to roughly 0.14, a significant caveat for real-world deployment.

**Keywords:** Optical Character Recognition, Cosmetic Ingredients, Product Label Information Extraction, Text Detection, Fuzzy String Matching

## 1.1 ความเป็นมาและความสำคัญของปัญหา

ในปัจจุบันผลิตภัณฑ์เครื่องสำอางและผลิตภัณฑ์ดูแลผิวได้รับความนิยมอย่างแพร่หลาย ผู้บริโภคจำนวนมากให้ความสำคัญกับการตรวจสอบส่วนผสมของผลิตภัณฑ์ก่อนการใช้งาน เนื่องจากสารบางชนิดอาจก่อให้เกิดการระคายเคือง อาการแพ้ หรือผลกระทบต่อสุขภาพผิว โดยเฉพาะผู้ที่มีผิวแพ้ง่าย อย่างไรก็ตาม รายชื่อส่วนผสมบนฉลากเครื่องสำอางมักแสดงด้วยตัวอักษรขนาดเล็ก มีความหนาแน่นสูง และประกอบด้วยชื่อสารเคมีที่มีความซับซ้อน ส่งผลให้ผู้ใช้ทั่วไปไม่สามารถอ่านและตรวจสอบข้อมูลได้อย่างสะดวก

เทคโนโลยี Optical Character Recognition (OCR) เป็นเทคโนโลยีที่ช่วยให้คอมพิวเตอร์สามารถรู้จำข้อความจากภาพได้โดยอัตโนมัติ ในปัจจุบัน เทคโนโลยี OCR ที่ใช้เทคนิค Deep Learning เช่น PaddleOCR สามารถรองรับข้อความที่มีรูปแบบหลากหลายและมีความซับซ้อนได้ดียิ่งขึ้น อย่างไรก็ตาม ในทางปฏิบัติ ภาพฉลากที่ผู้ใช้ถ่ายเองมักมีคุณภาพต่ำ เช่น ถ่ายในที่แสงน้อย ภาพสั่นหรือเบลอ และมุมกล้องเอียง ซึ่งส่งผลโดยตรงต่อความแม่นยำของ OCR นอกจากนี้ยังพบว่าโมดูล OCR สำเร็จรูปอย่าง PaddleOCR มีพารามิเตอร์การตั้งค่าจำนวนมากที่ส่งผลต่อความแม่นยำอย่างมีนัยสำคัญ เช่น การเปิดหรือปิดฟีเจอร์แก้ไขมุมมองเอกสาร และ threshold ของโมดูลตรวจจับข้อความ ซึ่งหากตั้งค่าไม่เหมาะสมจะทำให้ระบบทำงานได้ต่ำกว่าศักยภาพที่แท้จริงของโมเดลมาก

โครงงานนี้จึงพัฒนาระบบต้นแบบสำหรับดึงข้อมูลส่วนผสมของเครื่องสำอางจากภาพฉลากผลิตภัณฑ์ด้วยเทคนิค OCR โดยมีเป้าหมายเพื่อนำไปพัฒนาต่อยอดเป็น**ระบบแนะนำสกินแคร์ที่เหมาะสมกับผู้ใช้แต่ละราย**ในอนาคต งานวิจัยนี้เน้นกระบวนการวินิจฉัยและแก้ไขการตั้งค่า pipeline OCR อย่างเป็นระบบผ่านการทดลองแบบมีการควบคุม (controlled ablation) ร่วมกับการเพิ่มขั้นตอนเสริมที่ออกแบบเฉพาะสำหรับลักษณะข้อมูล คือภาพแถบข้อความแคบและความละเอียดต่ำ แทนการอาศัยเทคนิคปรับปรุงคุณภาพภาพเชิงคลาสสิกจำนวนมาก เพื่อให้ได้ pipeline OCR ที่แม่นยำที่สุดสำหรับนำไปพัฒนาต่อและผนวกเข้ากับระบบแนะนำสกินแคร์ในขั้นต่อไป

## 1.2 วัตถุประสงค์ของโครงงาน

1. เพื่อพัฒนาระบบ OCR สำหรับดึงข้อความส่วนผสมจากภาพฉลากเครื่องสำอาง
2. เพื่อวินิจฉัยและแก้ไขการตั้งค่า pipeline ของ PaddleOCR ทั้งด้าน engine configuration และการตรวจจับข้อความ ที่ส่งผลต่อความแม่นยำของการรู้จำข้อความจากภาพฉลากผลิตภัณฑ์
3. เพื่อพัฒนากระบวนการตรวจจับชื่อสารด้วยเทคนิค Fuzzy String Matching ร่วมกับฐานข้อมูล INCI ที่ผ่านการเสริมคำศัพท์ที่ขาดหายไป
4. เพื่อประเมินประสิทธิภาพของระบบด้วยตัวชี้วัดระดับชื่อสาร ได้แก่ Set Precision/Recall/F1-score และ Ingredient Error Rate ร่วมกับ Character Error Rate (CER) และ Word Error Rate (WER)

## 1.3 ขอบเขตของโครงงาน

โครงงานนี้ส่งมอบ**ระบบต้นแบบแบบ end-to-end** สำหรับดึงข้อมูลส่วนผสมจากภาพฉลากเครื่องสำอาง กล่าวคือรับภาพเป็น input และให้รายชื่อสารที่ตรวจพบเป็น output ผ่าน pipeline ที่ทำงานได้จริงตามลำดับ: รับภาพ → เพิ่มขอบภาพด้วยเทคนิค Border Padding → ดึงข้อความด้วย OCR → จับคู่ชื่อสารด้วย Fuzzy Matching → รายชื่อส่วนผสม ตามรายละเอียดในหัวข้อ 3.2 พร้อมชุดสคริปต์สำหรับรันซ้ำและประเมินผลที่ระบุไว้ในภาคผนวก ก มิใช่เพียงรายงานผลการทดลองเปรียบเทียบพารามิเตอร์เท่านั้น ทว่ากระบวนการพัฒนาระบบนี้เน้นไปที่การวินิจฉัยและปรับแต่งการตั้งค่าของโมดูลสำเร็จรูปที่มีอยู่แล้วอย่างเป็นระบบ แทนการออกแบบสถาปัตยกรรมโมเดลใหม่หรือฝึกโมเดลเอง โดยทุกขั้นตอนของ pipeline ถูกเลือกให้เจาะจงกับลักษณะเฉพาะของโดเมนปัญหานี้ ไม่ใช่การตั้งค่า OCR แบบทั่วไป กล่าวคือภาพฉลากเป็นแถบข้อความแคบความละเอียดต่ำ จึงต้องมี border padding เพื่อไม่ให้ตัวอักษรที่ชิดขอบภาพถูกตัดทิ้ง ชื่อสารเป็นศัพท์เฉพาะทางเคมีที่พจนานุกรมทั่วไปไม่ครอบคลุม จึงต้องเสริมฐานข้อมูล INCI และใช้ fuzzy matching แทนการสะกดคำแบบมาตรฐาน และภาพจำนวนมากมีข้อความชิดขอบจนตัวตรวจจับมาตรฐานมองข้าม จึงต้องปรับ detection threshold เฉพาะ รายละเอียดเหตุผลการออกแบบอยู่ในหัวข้อ 3.1.1 ขอบเขตของระบบและกระบวนการพัฒนามีดังนี้

1. ใช้ภาพฉลากผลิตภัณฑ์เครื่องสำอางภาษาอังกฤษเป็นหลัก
2. ใช้ **PaddleOCR 3.7.0 (PP-OCRv6_medium)** เป็นเครื่องมือหลักสำหรับการดึงข้อความจากภาพ รันบน CPU
3. วินิจฉัยและแก้ไขการตั้งค่า pipeline หลัก 4 ส่วน ได้แก่ (1) การตั้งค่าฟีเจอร์ในตัวของโมเดล คือ document unwarping, textline orientation และการปิด mkldnn เพื่อหลีกเลี่ยงบัค crash บนสภาพแวดล้อมที่ใช้ (2) การเพิ่มขอบภาพขาวหรือ border padding ก่อนเข้าสู่ OCR (3) การเสริมฐานข้อมูลคำศัพท์ INCI ที่ขาดหายไป และ (4) การปรับ threshold การตรวจจับข้อความ หรือ text detection box threshold
4. ใช้เทคนิค Fuzzy Matching ด้วยไลบรารี RapidFuzz ฟังก์ชัน `fuzz.ratio` กำหนด score cutoff ที่ 90 สำหรับตรวจจับชื่อสารจากฐานข้อมูลเครื่องสำอาง INCI หลัก 11,091 รายการ เสริมด้วยคำศัพท์ที่คัดสรรเพิ่มเติม 199 รายการ รวมเป็น 11,290 รายการไม่ซ้ำ
5. ใช้ชุดข้อมูลภาพฉลากเครื่องสำอางจริงจำนวน **216 ภาพ** และภาพจำลองสภาพแวดล้อมด้วยเทคนิค data augmentation ผ่านไลบรารี albumentations เพิ่มเติม 4 สภาพแวดล้อม คือภาพเบลอ แสงน้อย แสงกลางคืน และแสงในอาคาร รวมเป็น 5 สภาพแวดล้อม **1,080 ภาพ** โดย validate เต็มรูปแบบครบทั้ง 5 สภาพแวดล้อมแล้ว ดูหัวข้อ 4.4
6. ประเมินผลด้วยตัวชี้วัดระดับชื่อสาร ได้แก่ Set Precision/Recall/F1-score และ Ingredient Error Rate เป็นหลัก ร่วมกับ CER/WER เป็นตัวชี้วัดเสริมระดับตัวอักษร/คำ
7. ระบบที่ส่งมอบครอบคลุมเฉพาะส่วน pipeline การประมวลผลภาพ→ข้อความ หรือ backend เท่านั้น **ไม่รวม** ส่วนติดต่อผู้ใช้ทั้ง UI และ mobile app หรือ API สำหรับผนวกเข้ากับระบบแนะนำสกินแคร์ ซึ่งอยู่นอกขอบเขตของโครงงานระยะนี้และเป็นเป้าหมายของการพัฒนาต่อยอดในอนาคตตามหัวข้อ 1.4 และ 4.5

## 1.4 ประโยชน์ที่คาดว่าจะได้รับ

1. ได้โมดูล OCR ที่ผ่านการวินิจฉัยและแก้ไขการตั้งค่าอย่างเป็นระบบ พร้อมนำไปพัฒนาต่อยอดและผนวกเข้ากับ**ระบบแนะนำสกินแคร์ที่เหมาะสมกับผู้ใช้**ได้จริง
2. สามารถนำแนวทางการวินิจฉัยและปรับแต่ง pipeline OCR ทั้งด้าน engine configuration และ detection threshold tuning ไปประยุกต์ใช้กับงานวิเคราะห์ข้อความจากภาพในโมดูลอื่นของระบบแนะนำสกินแคร์ หรือระบบที่เกี่ยวข้องได้
3. เป็นแนวทางและหลักฐานเชิงประจักษ์ประกอบการตัดสินใจออกแบบ pipeline การอ่านฉลากของระบบแนะนำสกินแคร์ในขั้นพัฒนาต่อไป
4. เป็นประโยชน์ต่อการศึกษาและวิจัยด้าน Computer Vision และ Image Processing โดยเฉพาะในประเด็นที่ว่า**การตั้งค่าฟีเจอร์ในตัวของโมเดล OCR สำเร็จรูปอย่างเหมาะสม (engine configuration) อาจให้ผลกระทบต่อความแม่นยำมากกว่าการเพิ่มเทคนิค preprocessing เชิงภาพจำนวนมาก** และควรมีการทดสอบเชิงประจักษ์เพื่อวินิจฉัยจุดที่แท้จริงก่อนลงทุนพัฒนาเทคนิคเสริมที่ซับซ้อน

# บทที่ 2 ทฤษฎีและงานวิจัยที่เกี่ยวข้อง

## 2.1 Optical Character Recognition (OCR)

Optical Character Recognition (OCR) เป็นเทคโนโลยีที่ใช้สำหรับแปลงข้อความที่อยู่ในรูปแบบภาพให้อยู่ในรูปแบบข้อมูลดิจิทัลที่สามารถนำไปประมวลผลด้วยคอมพิวเตอร์ได้ โดยกระบวนการ OCR ประกอบด้วยหลายขั้นตอน ได้แก่ การตรวจจับตำแหน่งข้อความ (Text Detection) และการรู้จำตัวอักษร (Text Recognition)

ปัจจุบัน OCR ถูกนำไปประยุกต์ใช้อย่างแพร่หลายในงานด้านการแปลงเอกสารเป็นข้อมูลดิจิทัล การอ่านป้ายทะเบียนรถ การสแกนใบเสร็จ การรู้จำข้อความบนป้ายสินค้า และการวิเคราะห์ข้อมูลจากฉลากผลิตภัณฑ์ เทคโนโลยี OCR สมัยใหม่มีการประยุกต์ใช้เทคนิค Deep Learning เพื่อเพิ่มความสามารถในการรู้จำข้อความที่มีลักษณะซับซ้อน เช่น ตัวอักษรขนาดเล็ก ตัวอักษรเอียง หรือข้อความที่อยู่บนพื้นหลังหลากหลายรูปแบบ

ในโครงงานนี้ OCR ถูกนำมาใช้เพื่อดึงข้อมูลรายชื่อส่วนผสมของเครื่องสำอางจากภาพฉลากผลิตภัณฑ์ เพื่อพัฒนาเป็นโมดูลสำหรับผนวกเข้ากับระบบแนะนำสกินแคร์ที่เหมาะสมกับผู้ใช้

## 2.2 PaddleOCR

PaddleOCR เป็นไลบรารี OCR แบบ Open-source ที่พัฒนาโดย PaddlePaddle ซึ่งเป็นเฟรมเวิร์กด้าน Deep Learning ที่ได้รับการพัฒนาโดย Baidu โดย PaddleOCR ได้รับการออกแบบให้รองรับทั้งขั้นตอนการตรวจจับข้อความ (Text Detection) และการรู้จำข้อความ (Text Recognition) ภายในระบบเดียว รวมถึงมีโมดูลเสริมที่ทำงานก่อนขั้นตอนหลัก เช่น document orientation classification, document unwarping (แก้ไขความโค้ง/มุมมองของภาพเอกสาร) และ textline orientation classification (ตรวจจับทิศทางของแต่ละบรรทัดข้อความ)

โมดูลตรวจจับข้อความของ PaddleOCR (PP-OCRv6) ใช้สถาปัตยกรรม **DB (Differentiable Binarization)** ซึ่งทำนาย probability map ของตำแหน่งข้อความ แล้วแปลงเป็นกรอบข้อความ (bounding box/polygon) ด้วยขั้นตอน post-processing ที่มีพารามิเตอร์ควบคุมได้ ซึ่งมีรายละเอียดอยู่ในหัวข้อ 2.4 จุดนี้สำคัญเพราะเป็นส่วนที่โครงงานนี้ปรับแต่งเพื่อเพิ่มความแม่นยำ

ในโครงงานนี้ใช้ PaddleOCR เวอร์ชัน **3.7.0** โมเดล **PP-OCRv6_medium** เป็น OCR Engine เพียงตัวเดียวสำหรับการดึงข้อความจากภาพฉลากเครื่องสำอาง รันบน **CPU** เนื่องจากสภาพแวดล้อมที่ใช้พัฒนามีข้อจำกัดด้าน GPU ดังอธิบายไว้ในหัวข้อ 3.11 และ**เปิดใช้งาน** document unwarping และ textline orientation classification ซึ่งต่างจากแนวทางเดิมที่ปิดฟีเจอร์เหล่านี้เพื่อทดสอบ preprocessing แบบแยกส่วน เนื่องจากพบเชิงประจักษ์ว่าการเปิดใช้ทั้งสองฟีเจอร์นี้ช่วยลดค่า Character Error Rate ได้มากกว่าเทคนิค preprocessing เชิงคลาสสิกใด ๆ ที่เคยทดลอง

## 2.3 Border Padding (การเพิ่มขอบภาพก่อน OCR)

ภาพฉลากในชุดข้อมูลของโครงงานนี้ถูก crop มาเป็นแถบข้อความแคบ โดยมี median อัตราส่วนกว้าง:สูง ≈ 3:1 ซึ่งมักมีตัวอักษรอยู่ชิดขอบภาพมาก โมดูลตรวจจับข้อความของโมเดล OCR หลายตัว รวมถึง PP-OCRv6 มักมองข้ามข้อความที่อยู่ชิดขอบภาพ เนื่องจากขั้นตอน post-processing ของโมเดลอาจตัดกรอบข้อความที่อยู่ติดขอบภาพทิ้ง หรือ resize ภาพเข้าสู่โมเดลด้วยอัตราส่วนที่ทำให้บริเวณขอบเสียรายละเอียด

Border Padding คือการเพิ่มขอบภาพสีขาวรอบภาพก่อนส่งเข้าสู่โมดูล OCR เพื่อ "ดัน" ข้อความที่เคยอยู่ชิดขอบให้ห่างจากขอบภาพจริงมากขึ้น ช่วยให้โมดูลตรวจจับข้อความมีโอกาสพบกรอบข้อความบริเวณนั้นมากขึ้น โดยไม่ต้องปรับแก้โมเดลหรือ pipeline ภายใน

## 2.4 การตรวจจับข้อความแบบ DB (Differentiable Binarization) และ Threshold การ Post-processing

โมดูลตรวจจับข้อความที่ใช้อัลกอริทึม DB จะทำนาย probability map แล้วแปลงเป็นกรอบข้อความผ่านขั้นตอน post-processing ที่มีพารามิเตอร์สำคัญ ได้แก่

- **thresh** — ค่า threshold ระดับ pixel ของ probability map เพื่อสร้าง binary map เบื้องต้น
- **box_thresh** — เกณฑ์คะแนนความเชื่อมั่นเฉลี่ยภายในกรอบข้อความที่ตรวจพบ กรอบใดมีคะแนนต่ำกว่าเกณฑ์นี้จะถูกทิ้งไป (ไม่นับเป็นข้อความที่ตรวจพบ) — ค่าเริ่มต้นของ PP-OCRv6_medium คือ 0.45
- **unclip_ratio** — อัตราส่วนขยายกรอบข้อความออกจากขอบตัวอักษรจริง เพื่อชดเชยกรอบที่ตรวจพบแคบเกินไปจากขั้นตอน binarization
- **limit_side_len** — ขนาดด้านสูงสุดที่ภาพจะถูก resize ก่อนเข้าโมดูลตรวจจับ

พารามิเตอร์เหล่านี้ปรับได้ที่ระดับ inference โดยไม่ต้อง fine-tune หรือฝึกโมเดลใหม่ ในโครงงานนี้พบว่าการลดค่า **box_thresh** ช่วยกู้คืนกรอบข้อความจริงที่โมดูลตรวจจับ "เห็น" อยู่แล้วแต่ถูกทิ้งไปเพราะคะแนนความเชื่อมั่นไม่ถึงเกณฑ์เดิม เป็นการเพิ่ม Recall ล้วน ๆ โดยไม่ต้องมีข้อมูลหรือการฝึกโมเดลเพิ่มเติม รายละเอียดวิธีการและผลการทดลองอยู่ในหัวข้อ 3.9 และ 4.2

## 2.5 OpenCV

OpenCV (Open Source Computer Vision Library) เป็นไลบรารีสำหรับการประมวลผลภาพและคอมพิวเตอร์วิทัศน์ที่ได้รับความนิยมอย่างแพร่หลาย ในโครงงานนี้ OpenCV ถูกใช้สำหรับการอ่าน/เขียนไฟล์ภาพ (`cv2.imread`, `cv2.imwrite`) และการเพิ่มขอบภาพขาวก่อนเข้าสู่ OCR (`cv2.copyMakeBorder`)

## 2.6 Data Augmentation ด้วย Albumentations

Data Augmentation คือกระบวนการสร้างข้อมูลเพิ่มเติมจากข้อมูลต้นฉบับ โดยปรับแต่งคุณลักษณะบางอย่างของข้อมูลเพื่อจำลองสถานการณ์การใช้งานจริงที่หลากหลายขึ้น ในงานด้าน Computer Vision มักใช้เพื่อจำลองสภาพแวดล้อมของภาพที่แตกต่างกัน เช่น แสง มุมกล้อง หรือคุณภาพของภาพ

**Albumentations** เป็นไลบรารีสำหรับทำ Data Augmentation บนภาพที่ได้รับความนิยมในงานด้าน Computer Vision เนื่องจากมีความเร็วสูงและรองรับ transform หลากหลายรูปแบบ ในโครงงานนี้ใช้ Albumentations สร้างภาพจำลองสภาพแวดล้อม 4 รูปแบบจากภาพต้นฉบับ โดยจำลองลักษณะการถ่ายภาพจริงของผู้ใช้ทั่วไปอย่างละเอียด ทั้งอาการมือสั่น กล้องปรับโฟกัสอัตโนมัติ การบีบอัด JPEG ตอนส่งรูป และ ISO noise จากกล้องมือถือ มากกว่าการปรับความสว่างหรือคอนทราสต์อย่างง่ายเพียงอย่างเดียว รายละเอียดพารามิเตอร์อยู่ในหัวข้อ 3.4

## 2.7 Fuzzy String Matching

Fuzzy String Matching เป็นเทคนิคที่ใช้เปรียบเทียบความคล้ายคลึงระหว่างข้อความสองชุด โดยสามารถรองรับกรณีที่ข้อความมีข้อผิดพลาดหรือมีการสะกดที่ไม่ตรงกันทั้งหมด เทคนิคดังกล่าวได้รับความนิยมในงานด้านการค้นหาข้อมูล การตรวจสอบการสะกดคำ และการจับคู่ข้อความที่ไม่สมบูรณ์

ในโครงงานนี้ Fuzzy String Matching ถูกนำมาใช้เพื่อเปรียบเทียบข้อความที่ได้จาก OCR กับฐานข้อมูลรายชื่อสารเครื่องสำอาง (INCI) เนื่องจากข้อความที่ได้จาก OCR อาจมีข้อผิดพลาดจากคุณภาพของภาพหรือสภาพแวดล้อมในการถ่ายภาพ

## 2.8 RapidFuzz Library

RapidFuzz เป็นไลบรารีสำหรับการเปรียบเทียบข้อความที่ได้รับการพัฒนาขึ้นเพื่อให้มีประสิทธิภาพสูงและสามารถทำงานได้รวดเร็วกว่าไลบรารี FuzzyWuzzy ในหลายกรณี รองรับอัลกอริทึมการวัดความคล้ายคลึงของข้อความหลายรูปแบบ เช่น `ratio`, `partial_ratio`, `token_sort_ratio`, `token_set_ratio`

ในโครงงานนี้ กระบวนการ Fuzzy Matching หลัง OCR (post-processing) ทำงานดังนี้
1. รวมข้อความที่ OCR อ่านได้ทั้งหมด ตัด header เช่น "Ingredients:" ออกด้วย regular expression
2. แบ่งข้อความเป็น token ที่ comma หรือ colon โดยไม่ตัดกรณี comma ตามด้วยตัวเลข เพื่อกันไม่ให้ตัดกลางชื่อสารที่มีตัวเลข เช่น "1,2-Hexanediol"
3. แต่ละ token ที่ยาวตั้งแต่ 3 ตัวอักษรขึ้นไป จะถูกค้นหาชื่อที่ใกล้เคียงที่สุดในฐานข้อมูล INCI ทั้ง 11,290 ชื่อไม่ซ้ำรวมคำศัพท์เสริม ดูหัวข้อ 3.7 ด้วยฟังก์ชัน `rapidfuzz.process.extractOne` โดยใช้ scorer แบบ `fuzz.ratio` และกำหนด **score_cutoff = 90**
4. รับผลการจับคู่ก็ต่อเมื่อผ่านเงื่อนไขเพิ่มเติมเรื่องอัตราส่วนความยาวตัวอักษรระหว่าง token กับชื่อที่จับคู่ได้ ไม่เกิน 1.6 เท่า เพื่อกันการจับคู่ผิดระหว่าง token สั้นกับชื่อสารที่ยาวกว่ามาก
5. หากไม่ผ่านเงื่อนไข จะเก็บ token เดิมไว้โดยไม่แก้ไข

### 2.8.1 หลักการทำงานของ Levenshtein Distance

Levenshtein Distance เป็นวิธีการวัดความแตกต่างระหว่างข้อความสองชุด โดยคำนวณจากจำนวนครั้งขั้นต่ำของการดำเนินการที่จำเป็นในการแปลงข้อความหนึ่งให้เป็นอีกข้อความหนึ่ง ซึ่งประกอบด้วยการเพิ่มอักขระ (Insertion) การลบอักขระ (Deletion) และการแทนที่อักขระ (Substitution)

เทคนิคดังกล่าวเป็นพื้นฐานสำคัญของไลบรารี RapidFuzz ในการคำนวณค่าความคล้ายคลึงของข้อความสำหรับขั้นตอน Fuzzy Matching และยังเป็นพื้นฐานของตัวชี้วัด **Character Error Rate (CER)** และ **Word Error Rate (WER)** ที่ใช้ในการประเมินผลของโครงงานนี้ รายละเอียดสูตรคำนวณอยู่ในบทที่ 3

## 2.9 งานวิจัยที่เกี่ยวข้อง

Baek และคณะ (2019) ได้ศึกษาและเปรียบเทียบโมเดล Scene Text Recognition หลายรูปแบบ โดยพบว่าคุณภาพของภาพมีผลโดยตรงต่อประสิทธิภาพของ OCR โดยเฉพาะในกรณีของข้อความขนาดเล็กและพื้นหลังที่ซับซ้อน ซึ่งสอดคล้องกับข้อค้นพบในโครงงานนี้ที่ภาพความละเอียดต่ำส่งผลกระทบต่อความแม่นยำของ OCR อย่างชัดเจน และเป็นคอขวดหลักที่เหลืออยู่ดังอธิบายในหัวข้อ 4.3

Du และคณะ (2020) ได้นำเสนอ PP-OCR ซึ่งเป็นระบบ OCR ที่มีขนาดเล็กและประสิทธิภาพสูง เป็นต้นตระกูลของโมเดล PP-OCRv6 ที่ใช้เป็น OCR Engine หลักในงานวิจัยนี้ รวมถึงใช้สถาปัตยกรรม DB (Differentiable Binarization) สำหรับการตรวจจับข้อความ ซึ่งเป็นส่วนที่โครงงานนี้ปรับ threshold เพื่อเพิ่มความแม่นยำตามที่กล่าวไว้ในหัวข้อ 2.4

V. I. Levenshtein (1966) ได้นำเสนอแนวคิด Levenshtein Distance ซึ่งเป็นพื้นฐานสำคัญของไลบรารี RapidFuzz และตัวชี้วัด CER/WER ที่ใช้ในโครงงานนี้

Buslaev และคณะ (2020) ได้นำเสนอ **Albumentations** ไลบรารีสำหรับทำ Data Augmentation บนภาพที่มีความเร็วสูงและรองรับ transform หลากหลายรูปแบบ ซึ่งใช้ในการสร้างชุดข้อมูลจำลองสภาพแวดล้อม 4 รูปแบบของโครงงานนี้

นอกจากงานวิจัยพื้นฐานด้าน OCR ทั่วไปข้างต้น ยังมีงานวิจัยที่เจาะจงกับการดึงข้อมูลจากฉลากผลิตภัณฑ์/รายชื่อส่วนผสมโดยตรง ซึ่งใกล้เคียงกับโครงงานนี้มากกว่า:

Guimarães และคณะ (2023) ได้ทบทวนงานวิจัยด้านการตรวจจับและรู้จำข้อความบนฉลากสินค้าประเภทของชำ หรือ grocery label detection and recognition อย่างเป็นระบบ และชี้ให้เห็นความท้าทายเฉพาะของฉลากสินค้า เช่น พื้นผิวโค้ง ตัวอักษรขนาดเล็กหนาแน่น และพื้นหลังที่ซับซ้อน ซึ่งต่างจากงานวิจัย scene text ทั่วไปที่มักเน้นข้อความขนาดใหญ่หรือป้ายบอกทาง ตรงกับลักษณะข้อมูลฉลากเครื่องสำอางในโครงงานนี้ที่เป็นแถบข้อความแคบ ความสูงมัธยฐานเพียง 170.5 พิกเซล

Kayalvizhi และคณะ (2024) ได้พัฒนาระบบรู้จำส่วนผสมจากฉลากผลิตภัณฑ์ด้วย OCR ร่วมกับโมเดล LSTM เพื่อดึงข้อมูลส่วนผสมและแจ้งเตือนสารที่อาจเป็นอันตรายต่อผู้บริโภค เป็นแนวทางที่มีเป้าหมายเชิงประยุกต์ใกล้เคียงกับโครงงานนี้ คือการนำผลจาก OCR ไปใช้เพื่อความปลอดภัยของผู้บริโภค

Nagayi และคณะ (2025) ได้ประเมินประสิทธิภาพ OCR หลายระบบ รวมถึง PaddleOCR บนภาพฉลากบรรจุภัณฑ์อาหารจริงในแอฟริกาใต้ และพบประเด็นที่สอดคล้องกับโครงงานนี้อย่างชัดเจน: การรัน PaddleOCR บน CPU เนื่องจากข้อจำกัดความเข้ากันได้ของ GPU ส่งผลให้เวลาประมวลผลช้าลงมาก และการตั้งค่า preprocessing/pipeline ของแต่ละ OCR engine เช่น การ resize, normalization และ angle classification ของ PaddleOCR ส่งผลต่อความแม่นยำอย่างมีนัยสำคัญ ซึ่งสนับสนุนข้อค้นพบหลักของโครงงานนี้ที่ว่าการตั้งค่า engine มีผลกระทบสูงต่อผลลัพธ์

Arief (2026) ได้นำเสนอ HalalBench ซึ่งเป็น benchmark สำหรับการดึงข้อมูลส่วนผสมจากฉลากบรรจุภัณฑ์อาหารหลายภาษา และพบว่าขั้นตอน post-processing ที่ออกแบบมาอย่างเหมาะสมให้ผลปรับปรุงค่า F1 ถึง 36% มากกว่าการเปลี่ยน OCR engine เพียงอย่างเดียว ซึ่งสอดคล้องในทิศทางเดียวกับข้อค้นพบของโครงงานนี้ที่ว่าการปรับแต่งขั้นตอนรอบข้าง ทั้ง configuration และ post-processing มีผลกระทบสูงไม่แพ้ตัวโมเดล OCR เอง

จากการศึกษางานวิจัยที่เกี่ยวข้องพบว่า แม้จะมีงานวิจัยเฉพาะทางด้านการดึงข้อมูลจากฉลากผลิตภัณฑ์และส่วนผสมอยู่บ้าง ทั้งของ Guimarães และคณะ (2023), Kayalvizhi และคณะ (2024), Nagayi และคณะ (2025) และ Arief (2026) แต่งานวิจัยเหล่านี้ส่วนใหญ่เน้นเปรียบเทียบ OCR engine หรือเทคนิค post-processing โดยรวม ยังมีงานวิจัยจำนวนน้อยที่วินิจฉัยผลของการตั้งค่าหรือ configuration ภายในโมดูล OCR สำเร็จรูปตัวเดียวอย่างละเอียดเป็นระบบ เช่น engine feature flags และ detection threshold ทั้งที่ในทางปฏิบัติพบว่าการตั้งค่าที่ไม่เหมาะสมส่งผลกระทบต่อความแม่นยำมากกว่าการเพิ่มเทคนิค preprocessing เชิงภาพเสียอีก โครงงานนี้จึงมุ่งเน้นกระบวนการวินิจฉัยและแก้ไขการตั้งค่า pipeline อย่างเป็นระบบ ก่อนนำไปพัฒนาต่อและใช้งานจริงในระบบแนะนำสกินแคร์ที่เหมาะสมกับผู้ใช้

# บทที่ 3 วิธีดำเนินงาน

## 3.1 ภาพรวมของระบบ

งานวิจัยนี้ดำเนินการวินิจฉัยและปรับแต่ง pipeline OCR เชิงประจักษ์เป็นลำดับขั้น โดยใช้ PaddleOCR เป็นเครื่องมือรู้จำข้อความหลัก บนภาพฉลากส่วนผสมเครื่องสำอางชุดเดียวกัน เพื่อค้นหาการตั้งค่าที่เหมาะสมสำหรับนำไปพัฒนาต่อและผนวกเข้ากับระบบแนะนำสกินแคร์ที่เหมาะสมกับผู้ใช้ กระบวนการดำเนินงานแบ่งเป็น 4 ขั้นตอนหลัก ได้แก่ (1) การเตรียมชุดข้อมูลและจำลองสภาพแวดล้อม (2) การวินิจฉัยและแก้ไขการตั้งค่า engine หลัก (3) การเสริมฐานข้อมูลคำศัพท์และปรับ threshold การตรวจจับข้อความ และ (4) การประเมินผลด้วยตัวชี้วัดระดับชื่อสารและ CER/WER

ก่อนเริ่มงานวิจัยนี้ ระบบต้นแบบที่มีอยู่เดิมยังไม่ผ่านการวินิจฉัยอย่างเป็นระบบ และมีจุดตั้งค่าที่ผิดพลาดอยู่ 4 จุด ได้แก่ บัคของไลบรารีเร่งความเร็ว mkldnn ที่ทำให้โปรแกรม crash จนต้องปิดฟีเจอร์นี้แบบชั่วคราวโดยไม่ได้พิจารณาผลกระทบอื่น การปิดฟีเจอร์แก้ไขความโค้งของภาพเอกสารและฟีเจอร์ตรวจจับทิศทางบรรทัดข้อความในตัวโมเดลไว้เพื่อทดสอบเทคนิค preprocessing แบบแยกส่วนในช่วงแรกแต่ไม่ได้เปิดกลับ ฐานข้อมูลคำศัพท์ INCI ที่ยังไม่ครอบคลุมชื่อสารที่พบบ่อยในฉลากจริง และบัคในขั้นตอน post-processing ของการแก้ไขข้อความหลัง OCR ระบบต้นแบบในสภาพดังกล่าวให้ค่า Set F1 บนภาพจริง 216 ภาพเพียง 0.39 ซึ่งเป็นจุดเริ่มต้น (baseline) ที่งานวิจัยนี้ใช้อ้างอิงเปรียบเทียบผลการปรับปรุงทั้งหมดในบทที่ 4

### 3.1.1 เหตุผลการออกแบบ Pipeline ให้เหมาะสมกับลักษณะเฉพาะของโดเมนปัญหา

Pipeline ที่พัฒนาขึ้น (หัวข้อ 3.2) ไม่ได้เป็นการตั้งค่า OCR ทั่วไปที่หยิบมาใช้ตรงๆ แต่ทุกขั้นตอนถูกออกแบบให้ตอบสนองต่อลักษณะเฉพาะของภาพฉลากเครื่องสำอางในโครงงานนี้โดยตรง ดังนี้

- **ภาพเป็นแถบข้อความแคบ ความละเอียดต่ำ และตัวอักษรมักอยู่ชิดขอบภาพ** (ความสูงมัธยฐานเพียง 170.5 พิกเซล อัตราส่วนกว้าง:สูง มัธยฐาน ≈ 3.08:1 ดูหัวข้อ 3.3.1) ต่างจากภาพเอกสารทั่วไปที่โมดูล OCR สำเร็จรูปส่วนใหญ่ถูกออกแบบมาให้ทำงานได้ดี จึงต้องเพิ่ม Border Padding (หัวข้อ 3.6) เพื่อไม่ให้ตัวอักษรที่ชิดขอบถูกโมดูลตรวจจับมองข้ามหรือถูกตัดทิ้งระหว่างขั้นตอน post-processing
- **ชื่อสารเป็นศัพท์เฉพาะทางเคมี (INCI name) ที่มีความซับซ้อนและไม่อยู่ในพจนานุกรมทั่วไป** ทำให้การแก้ไขคำผิดด้วยพจนานุกรมภาษาอังกฤษมาตรฐานใช้ไม่ได้ผล จึงต้องสร้างและเสริมฐานข้อมูล INCI เฉพาะทาง (หัวข้อ 3.7) ควบคู่กับ Fuzzy String Matching (หัวข้อ 3.8) แทนการตรวจตัวสะกดแบบทั่วไป
- **โมดูลตรวจจับข้อความสำเร็จรูปมีค่าเริ่มต้นที่ปรับแต่งมาสำหรับข้อความในเอกสาร/ป้ายทั่วไป** ซึ่งมีขนาดใหญ่และห่างจากขอบภาพมากกว่า จึงมองข้ามข้อความที่มีลักษณะแตกต่างจากที่โมเดลถูกฝึกมาบ่อยครั้ง งานวิจัยนี้จึงต้องวินิจฉัยและปรับ detection box threshold ให้เหมาะกับข้อมูลโดเมนนี้โดยเฉพาะ (หัวข้อ 3.9) แทนการใช้ค่าเริ่มต้น

การออกแบบ pipeline โดยยึดลักษณะของโดเมนปัญหาเป็นหลักเช่นนี้ คือเหตุผลที่งานวิจัยนี้เลือกวินิจฉัยและปรับแต่งการตั้งค่าของโมดูลสำเร็จรูปที่มีอยู่แล้วอย่างเป็นระบบ แทนการทดลองเทคนิค preprocessing เชิงภาพทั่วไปจำนวนมากโดยไม่คำนึงถึงลักษณะเฉพาะของข้อมูล

## 3.2 สถาปัตยกรรมของระบบ

ระบบที่พัฒนาขึ้นประกอบด้วยขั้นตอนหลัก ดังนี้

1. การรับภาพฉลากเครื่องสำอางเป็น input ซึ่งอาจเป็นภาพจริงหรือภาพจำลองสภาพแวดล้อม
2. เพิ่มขอบภาพขาว 25% รอบภาพด้วยเทคนิค Border Padding ดังอธิบายในหัวข้อ 3.6
3. การดึงข้อความด้วย OCR ผ่าน PaddleOCR PP-OCRv6_medium บน CPU โดยเปิดใช้งาน document unwarping และ textline orientation และตั้งค่า text detection box_thresh = 0.30 ดังอธิบายในหัวข้อ 3.5
4. การจับคู่ข้อความด้วย Fuzzy Matching ผ่านไลบรารี RapidFuzz เทียบกับฐานข้อมูล INCI ตามหัวข้อ 3.7-3.8
5. การคำนวณตัวชี้วัดระดับชื่อสาร ได้แก่ Set Precision/Recall/F1 และ IER รวมถึง CER/WER เทียบกับ Ground Truth
6. การบันทึกผลลัพธ์รายภาพและสรุปผลเฉลี่ยแยกตามสภาพแวดล้อม

แผนภาพสถาปัตยกรรมโดยสรุป: ภาพนำเข้า → เพิ่มขอบภาพ (25%) → OCR ด้วย PaddleOCR (เปิด document unwarping และ textline orientation, box_thresh=0.30) → จับคู่ชื่อสารด้วย Fuzzy Matching (threshold=90) → คำนวณตัวชี้วัด CER/WER และ Set-F1/IER เทียบกับ Ground Truth

## 3.3 การสร้างชุดข้อมูล

### 3.3.1 ภาพต้นฉบับและ Ground Truth

ชุดข้อมูลภาพต้นฉบับเป็นภาพถ่ายฉลากส่วนผสมเครื่องสำอางจริงจำนวน **216 ภาพ** ที่ถูก crop มาเฉพาะส่วนที่มีรายชื่อสารเคมี ขนาดภาพมีความหลากหลายและเล็กกว่าภาพถ่ายฉลากทั่วไปมาก ความสูงต่ำสุดอยู่ที่ 70 พิกเซล สูงสุด 1,000 พิกเซล มัธยฐานอยู่ที่ 170.5 พิกเซล และความกว้างมัธยฐาน 532 พิกเซล คิดเป็นอัตราส่วนกว้าง:สูง มัธยฐาน ≈ 3.08:1

Ground Truth มีครบทั้งหมด **216 ไฟล์** จับคู่ครบทุกภาพ แต่ละไฟล์คือรายชื่อสาร (INCI name) หนึ่งชื่อต่อบรรทัด ได้จากการถอดข้อความด้วยมือและผู้ช่วย AI จากภาพฉลากจริง

Reference text ที่ใช้เทียบกับผล OCR คือการนำรายชื่อสารทุกชื่อในไฟล์ label มาต่อกันด้วย `, ` (comma + space) เป็น string เดียว

## 3.4 Data Augmentation

เพื่อจำลองสภาพแวดล้อมการถ่ายภาพจริงที่มีคุณภาพต่ำ ใช้ไลบรารี **albumentations** สร้างภาพจำลอง 4 สภาพแวดล้อมจากภาพต้นฉบับทุกภาพ (216 × 4 = 864 ภาพ) รวมกับภาพต้นฉบับเป็น **5 สภาพแวดล้อมทั้งหมด รวม 1,080 ภาพ**

| Scenario | จำลองสถานการณ์ | Transform หลัก |
|---|---|---|
| **blur** | มือสั่น/โฟกัสไม่ทันตอนถ่ายฉลากใกล้ ๆ ด้วยมือถือ | `MotionBlur`/`GaussianBlur`/`Defocus` (สุ่มเลือก) + `Downscale` (รายละเอียดหายจากการปรับโฟกัสเร็ว) + `ImageCompression` (บีบอัด JPEG ตอนส่งรูป) |
| **low_light** | ถ่ายในที่แสงน้อย (ร้าน/บ้านไฟสลัว) ยังไม่มืดสนิท | `RandomBrightnessContrast` (ลด) + `RandomGamma` + `ISONoise` (กล้องดัน ISO สู้แสง) + `ImageCompression` |
| **night** | ถ่ายกลางคืน แสงน้อยมาก มักมีแหล่งแสงจุดเดียว มือสั่นเพราะสปีดชัตเตอร์ต่ำ | `RandomBrightnessContrast` (ลดมากกว่า low_light) + `RandomGamma` + `ISONoise` (สูง) + `MotionBlur` + `RGBShift` (แสงไฟโซเดียม/ไฟถนน) + `ImageCompression` |
| **indoor** | ถ่ายในร่ม แสงไฟหลอด (เหลือง/ขาว) แสงไม่สม่ำเสมอ อาจมีเงาบัง | `RGBShift` (แสงหลอดไส้/วอร์มไวท์) + `RandomBrightnessContrast` (เล็กน้อย) + `RandomShadow` + `ImageCompression` |

แต่ละภาพสุ่มค่าภายในช่วง limit ที่กำหนดเพียงครั้งเดียวตอนสร้างชุดข้อมูล ภาพจำลองทั้งหมดถูกสร้างไว้ล่วงหน้าเป็นไฟล์คงที่และไม่สุ่มใหม่ทุกครั้งที่รัน OCR ดังนั้นการทดลองแต่ละเงื่อนไขจึงใช้ภาพชุดเดียวกันที่จับคู่ตามภาพต้นฉบับได้ ทำให้สามารถเปรียบเทียบผลระหว่างเงื่อนไขได้อย่างเป็นธรรม

## 3.5 เครื่องมือ OCR และการตั้งค่า

ใช้ **PaddleOCR 3.7.0** โมเดล **PP-OCRv6_medium** รันบน **CPU** การตั้งค่าที่ใช้จริงและเหตุผลของแต่ละค่า:

## 3.6 Border Padding

ก่อนส่งภาพเข้าสู่ `ocr.predict()` จะเพิ่มขอบภาพสีขาวรอบภาพด้วย `cv2.copyMakeBorder` โดยขนาดขอบคำนวณจาก `pad_px = round(min(height, width) × 0.25)` คือ 25% ของด้านที่สั้นกว่า ค่านี้ผ่านการทดลองเปรียบเทียบบนตัวอย่าง 40 ภาพจากชุด "original" พบว่า 25% ให้ผลดีที่สุด เพิ่ม Set F1 จาก 0.548 เป็น 0.563 ส่วนใหญ่มาจากการเพิ่ม Recall จาก 0.535 เป็น 0.581 ส่วนการ pad มากกว่านี้ที่ 50% หรือน้อยกว่านี้ที่ 10% ให้ผลแย่กว่า

## 3.7 ฐานข้อมูลส่วนผสมเครื่องสำอาง (INCI)

### 3.7.1 ฐานข้อมูลหลักและช่องโหว่ที่พบ

ฐานข้อมูลส่วนผสมหลักมีรายชื่อสาร INCI จำนวน **11,091 รายการไม่ซ้ำ** ซึ่งรวบรวมจากฐานข้อมูล CosIng ของสหภาพยุโรป อย่างไรก็ตาม ฐานข้อมูลลักษณะนี้มักถูกจัดทำขึ้นเพื่อวัตถุประสงค์ด้านกฎระเบียบ จึงอาจไม่ครอบคลุมชื่อสารที่ใช้กันทั่วไปในฉลากสินค้าจริงทั้งหมด โครงงานนี้จึงตรวจสอบความครอบคลุมของฐานข้อมูลหลักด้วยวิธีดังนี้

1. รวบรวมชื่อสารทุกชื่อที่ปรากฏใน Ground Truth ของภาพฉลากจริงทั้ง 216 ภาพ (หัวข้อ 3.3.1) ได้ชื่อสารที่ไม่ซ้ำกันทั้งหมด 1,574 ชื่อ จากจำนวนการปรากฏรวม (mentions) 8,198 ครั้ง
2. เทียบชื่อสารแต่ละชื่อ (แบบ case-insensitive, exact match) กับฐานข้อมูลหลัก 11,091 รายการ พบว่ามีชื่อสารที่ไม่ซ้ำกัน 1,081 ชื่อ (68.7% ของชื่อไม่ซ้ำทั้งหมด) ที่ไม่มีอยู่ในฐานข้อมูล
3. เมื่อนับตามจำนวนครั้งที่ปรากฏจริงแทนที่จะนับตามชื่อไม่ซ้ำ เพื่อสะท้อนผลกระทบต่อภาพจริงอย่างถูกสัดส่วน เนื่องจากบางชื่อ เช่น Glycerin หรือ Aqua ปรากฏซ้ำในหลายผลิตภัณฑ์ พบว่าการปรากฏที่ขาดหายไปมีทั้งหมด 4,803 ครั้ง จากทั้งหมด 8,198 ครั้ง คิดเป็น **58.6%** ซึ่งเป็นตัวเลขที่รายงานไว้ในหัวข้อนี้และในบทคัดย่อ

ตัวเลขนี้คำนวณด้วยสคริปต์ `compute_inci_coverage_and_paired_bootstrap.py` (ภาคผนวก ก) ซึ่งสามารถรันซ้ำเพื่อตรวจสอบได้

### 3.7.2 เกณฑ์การคัดสรรคำศัพท์เสริม 199 รายการ

เนื่องจากช่องโหว่ 58.6% ส่วนใหญ่มาจากชื่อสารที่พบไม่บ่อย (เช่น สารสกัดจากพืชเฉพาะทางที่ปรากฏเพียง 1-2 ครั้งในชุดข้อมูล) การเสริมชื่อทั้งหมดที่ขาดหายไปจึงมีความเสี่ยงที่จะทำให้ฐานข้อมูลมีชื่อคล้ายกันมากเกินไปจนกระทบความแม่นยำของ Fuzzy Matching (ดูผลการทดลองเปรียบเทียบด้านล่าง) จึงกำหนดเกณฑ์การคัดสรรดังนี้:

- คัดเฉพาะชื่อสารที่ไม่มีอยู่ในฐานข้อมูลหลัก **และปรากฏในไฟล์ Ground Truth ตั้งแต่ 5 ภาพขึ้นไป** (นับจากภาพทั้ง 216 ภาพในหัวข้อ 3.7.1) ด้วยเหตุผลว่าชื่อที่พบบ่อยเช่นนี้มีโอกาสสูงที่จะปรากฏซ้ำในภาพที่ระบบต้องประมวลผลจริงในอนาคต จึงคุ้มค่าต่อการเพิ่มเข้าฐานข้อมูลมากกว่าชื่อที่พบเพียงครั้งเดียว
- เมื่อใช้เกณฑ์นี้กับชื่อสารที่ขาดหายไปทั้ง 1,081 ชื่อ ได้ผลลัพธ์ตรงกับไฟล์ patch จริงพอดี คือ **199 รายการ** ยืนยันว่าเกณฑ์ความถี่ ≥ 5 ภาพ คือเกณฑ์ที่ใช้จริงในการคัดสรร
- หลังเสริมคำศัพท์ 199 รายการนี้แล้ว ฐานข้อมูลรวมมี **11,290 รายการไม่ซ้ำ** และสัดส่วนการปรากฏของชื่อสารที่ยังขาดหายไปลดลงเหลือ 17.0% จาก 58.6% ส่วนที่เหลือคือชื่อสารเฉพาะทางที่พบน้อยกว่า 5 ครั้ง เช่น Cystoseira Tamariscifolia Extract และ Haematococcus Pluvialis Extract ซึ่งยังไม่ถูกเสริมเข้าไปตามเกณฑ์ข้างต้น หากนำเกณฑ์นี้ไปใช้กับชุดข้อมูลอื่น ควรกำหนดค่าความถี่ขั้นต่ำจากชุดพัฒนาแยกต่างหากก่อนประเมินผลบนชุดทดสอบ

ข้อสังเกตสำคัญจากการทดลอง: การเสริมคำศัพท์แบบคัดสรรเฉพาะชื่อที่พบบ่อยเช่นนี้ให้ผลดีกว่าการเสริมชื่อทั้งหมดที่หาได้จำนวน 2,023 ชื่อ ซึ่งรวมชื่อที่พบเพียงครั้งเดียวด้วย เนื่องจากตัวเลือกที่คล้ายกันจำนวนมากทำให้ fuzzy matching จับคู่ผิดได้ง่ายขึ้น อย่างไรก็ตาม การคัดเลือกคำศัพท์ 199 รายการใช้ความถี่จาก Ground Truth ของภาพ 216 ภาพชุดเดียวกับที่ใช้รายงานผล จึงเป็นการปรับฐานคำศัพท์เชิงสำรวจบนชุดข้อมูลนี้ ไม่ใช่การประเมินแบบอิสระ ผลลัพธ์หลังเสริมคำศัพท์จึงควรตีความอย่างระมัดระวัง และงานต่อไปควรสร้าง patch จากชุดพัฒนาเท่านั้น แล้วประเมินบนชุดทดสอบที่ไม่ถูกใช้คัดเลือกคำศัพท์

## 3.8 Fuzzy String Matching (การนำไปใช้จริง)

รายละเอียดขั้นตอนตรงกับหัวข้อทฤษฎี 2.8 โดยพารามิเตอร์ที่ใช้จริงคือ score_cutoff = 90 ซึ่งสูงกว่าค่าตั้งต้น 85 ที่เคยทดลองในช่วงแรก เนื่องจาก sweep พบว่า 90 ให้ mean CER ต่ำกว่า 85 โดยไม่มีข้อเสีย และแบ่ง token ด้วย comma หรือ colon

## 3.9 การปรับ Detection Box Threshold

เนื่องจากพบว่าคอขวดสำคัญที่เหลืออยู่หลังแก้ไข pipeline หลักคือค่า Recall ของการตรวจจับข้อความ จึงทดลองปรับพารามิเตอร์ post-processing ของโมดูลตรวจจับข้อความ (หัวข้อ 2.4) โดยไม่ fine-tune โมเดล วิธีดำเนินการ:

1. **Sweep เบื้องต้น** บนตัวอย่าง 40 ภาพ ("original") เปรียบเทียบ 5 ค่า config: baseline (ค่าเริ่มต้น), ลด `box_thresh` เป็น 0.30, เพิ่ม `unclip_ratio` เป็น 1.8, ผสมทั้งสอง, และเพิ่ม `limit_side_len` เป็น 1536
2. **Sweep ละเอียดเพิ่มเติม** ทดสอบ `box_thresh` ที่ 0.30, 0.25, 0.20, 0.15 เพื่อหาว่ายังมีกำไรเพิ่มหรือไม่หากลดต่ำกว่า 0.30
3. **ตรวจสอบความน่าเชื่อถือ (sanity check)**: ยืนยันว่าผลต่างที่พบไม่ได้มาจากความไม่คงที่ของโมเดล (non-determinism) โดยรันค่า config เดิมซ้ำหลายรอบบนภาพชุดเดียวกัน พบว่าผลลัพธ์เหมือนเดิมทุกครั้ง (deterministic) จึงสรุปได้ว่าผลต่างที่วัดได้เป็นผลจากพารามิเตอร์จริง
4. **Validate เต็มรูปแบบ** บนภาพทั้งหมด 216 ภาพด้วยค่าที่ดีที่สุดจากการ sweep

## 3.10 การประเมินผล

### 3.10.1 การ Normalize ข้อความก่อนเทียบ

```python
def normalize_text(text):
    text = text.lower().strip()
    text = re.sub(r"\s+", " ", text)
    return text
```

ทำกับทั้ง OCR output (hypothesis) และ reference text ก่อนคำนวณเสมอ เพื่อไม่ให้ case-sensitivity หรือช่องว่างเกินกระทบคะแนน

### 3.10.2 Character Error Rate (CER) และ Word Error Rate (WER)

```
CER = Levenshtein_distance(normalize(hypothesis), normalize(reference)) / len(normalize(reference))
WER = Levenshtein_distance(normalize(hypothesis).split(), normalize(reference).split()) / len(normalize(reference).split())
```

คำนวณด้วย `rapidfuzz.distance.Levenshtein.distance` ค่ายิ่งน้อยยิ่งดี ทั้งสองค่าคำนวณแยกต่อภาพแล้วหาค่าเฉลี่ยเลขคณิต (macro-average)

### 3.10.3 ตัวชี้วัดระดับชื่อสาร (Ingredient-level Metrics) — ตัวชี้วัดหลัก

เนื่องจาก CER/WER เปรียบเทียบที่ระดับตัวอักษร/คำ ซึ่งได้รับผลกระทบจากความแตกต่างของรูปแบบการจัดวางข้อความ กล่าวคือ reference ต่อชื่อสารด้วย comma เรียงตามลำดับในไฟล์ ในขณะที่ OCR อ่านตามการตัดบรรทัดจริงบนฉลากซึ่งอาจไม่เรียงลำดับเดียวกัน ทำให้ CER/WER ลงโทษความคลาดเคลื่อนที่ไม่ได้เกิดจากการอ่านผิดจริง โครงงานนี้จึงใช้ตัวชี้วัดเสริมที่เปรียบเทียบที่ **ระดับชื่อสาร (ingredient token)** เป็นตัวชี้วัดหลักในการตัดสินใจปรับแต่ง pipeline ดังนี้:

1. ตัดข้อความทั้งสองฝั่ง (OCR output และ reference) เป็น token ด้วย regex ที่ครอบคลุม comma, colon และ period โดย period มักเป็น comma ที่ OCR อ่านผิด การแบ่ง token ด้วย period ถูกใช้เฉพาะตอนให้คะแนนเท่านั้น ไม่ใช่ตอนแก้ไขข้อความจริง เพราะทดสอบแล้วพบว่าการ split ที่ period ในขั้นตอนแก้ไขข้อความทำให้ fragment เล็กลงและจับคู่ผิดง่ายขึ้น
2. **Ingredient Error Rate (IER)** = Levenshtein distance ระหว่าง token list สองฝั่ง หารด้วยจำนวน token ของ reference โดยนับ token ทั้งก้อนถูก/ผิด ไม่มี partial credit
3. **Set Precision/Recall/F1** = จับคู่ token ของทั้งสองฝั่งแบบ one-to-one ด้วยคะแนนความคล้ายคลึง (เรียงจากคะแนนสูงไปต่ำ, threshold ≥ 85 คะแนน) แทนการเทียบแบบ exact match เพื่อให้เครดิตกับคำที่ใกล้เคียงถูกต้อง

ตัวชี้วัดกลุ่มนี้นำหน้าด้วยคำว่า **"Set"** เพราะเปรียบเทียบ token ของทั้งสองฝั่งในลักษณะ**เซตที่ไม่สนใจลำดับ** (unordered set matching) — จับคู่ token ที่คล้ายกันที่สุดแบบ one-to-one โดยไม่คำนึงว่า token นั้นอยู่ตำแหน่งใดในข้อความ ต่างจาก WER/CER ที่เป็นการเปรียบเทียบแบบเรียงลำดับ (sequence alignment) ซึ่งลงโทษการสลับตำแหน่ง การตั้งชื่อเช่นนี้จึงสื่อสารข้อแตกต่างเชิงวิธีการอย่างชัดเจน และเป็นเหตุผลที่ **ใช้ Set F1 เป็นตัวชี้วัดหลักของโครงงานนี้** เพราะตรงกับเป้าหมายเชิงปฏิบัติ คือระบุได้ว่าพบชื่อสารใดบ้างถูกต้อง โดยไม่ผูกกับลำดับการจัดเรียงบนฉลาก มากกว่า CER/WER หรือ IER แบบเข้มงวด

### 3.10.4 Bootstrap Confidence Interval

เนื่องจากค่าเฉลี่ยตัวชี้วัดที่รายงาน (เช่น mean Set F1) เป็นค่าประมาณจากภาพตัวอย่าง 216 ภาพ จึงมีความไม่แน่นอนในตัวเอง โครงงานนี้จึงคำนวณ **95% confidence interval (CI)** ด้วยวิธี bootstrap resampling เพื่อรายงานช่วงความเชื่อมั่นควบคู่กับค่าเฉลี่ย ดังนี้

1. สุ่มเลือกภาพจากชุดผลลัพธ์รายภาพแบบ resampling with replacement (สุ่มแบบใส่คืน) จากผลลัพธ์รายภาพทั้ง 216 ภาพ ให้ได้จำนวนภาพเท่าเดิมในแต่ละรอบ ทำซ้ำ 10,000 รอบ แล้วคำนวณค่าเฉลี่ยของแต่ละรอบ จากนั้นใช้ percentile ที่ 2.5 และ 97.5 ของค่าเฉลี่ยทั้ง 10,000 รอบเป็นขอบเขตล่างและบนของ 95% CI การสุ่มแบบใส่คืนอาจทำให้ภาพที่ยากหรือภาพที่ง่ายบางภาพถูกเลือกซ้ำมากในบางรอบ ซึ่งเป็นส่วนหนึ่งของการประมาณความไม่แน่นอนของค่าเฉลี่ยจากชุดข้อมูลนี้ ไม่ใช่การคัดเลือกภาพแบบมีอคติ
2. สำหรับการเปรียบเทียบค่าเฉลี่ยระหว่างสองเงื่อนไขบนภาพชุดเดียวกันทุกกรณี ไม่ว่าจะเป็นก่อน/หลังปรับพารามิเตอร์ เช่น box_thresh 0.45 → 0.30 ในหัวข้อ 4.2.3 หรือภาพต้นฉบับเทียบกับภาพจำลองสภาพแวดล้อมแต่ละแบบในหัวข้อ 4.4 โครงงานนี้ใช้ **paired bootstrap** เป็นมาตรฐานเดียวสำหรับทุกการเปรียบเทียบ เนื่องจากวิธีนี้สุ่มเลือกภาพร่วมกันทั้งสองฝั่งในแต่ละรอบ แล้วคำนวณผลต่างของค่าเฉลี่ยโดยตรง จึงลดความแปรปรวนที่มาจากความยากง่ายระหว่างภาพ หาก 95% CI ของผลต่างไม่ครอบคลุมค่า 0 แสดงว่าผลต่างที่วัดได้ไม่น่าจะเกิดจากความบังเอิญของกลุ่มตัวอย่าง

## 4.1 ผลกระทบของการแก้ไข Pipeline หลัก

ดังที่กล่าวไว้ในหัวข้อ 3.1 ระบบต้นแบบเดิมก่อนงานวิจัยนี้มีค่า Set F1 บนภาพจริง 216 ภาพ ("original") เพียง **0.39** เนื่องจากปัญหาการตั้งค่า pipeline 4 จุด คือ บัค mkldnn ที่ทำให้ crash และต้องปิดการใช้งาน การตั้งค่า engine ผิดโดยฟีเจอร์แก้ไขความโค้งของภาพเอกสารและฟีเจอร์ตรวจจับทิศทางบรรทัดข้อความเคยถูกปิดไว้ ช่องโหว่ฐานข้อมูลคำศัพท์ INCI ที่ขาดชื่อสารที่พบบ่อย และบัคในขั้นตอน post-processing ของการแก้ไขข้อความ หลังวินิจฉัยและแก้ไขปัญหาทั้ง 4 จุดนี้ ค่า Set F1 ดีขึ้นเป็น **0.55 (+41%)**

## 4.2 ผลการปรับ Detection Box Threshold

**Sweep** ในที่นี้หมายถึงการค้นหาค่าพารามิเตอร์ที่เหมาะสมด้วยการรันระบบซ้ำหลายรอบ โดยแต่ละรอบเปลี่ยนค่าพารามิเตอร์ (เช่น box_thresh) เป็นค่าที่กำหนดไว้ล่วงหน้าค่าหนึ่ง แล้ววัดผลลัพธ์ (Set F1 เป็นหลัก) ของทุกรอบบนภาพชุดเดียวกัน เพื่อเปรียบเทียบว่าค่าใดให้ผลดีที่สุด เป็นวิธีค้นหาค่าที่เหมาะสมแบบตรงไปตรงมาที่ใช้ได้กับพารามิเตอร์ระดับ inference ที่ไม่ต้องฝึกโมเดลใหม่

เหตุผลที่ **Recall** ของการตรวจจับข้อความเป็นคอขวดสำคัญ คือ pipeline ของโครงงานนี้ทำงานเป็นลำดับ: หากโมดูลตรวจจับข้อความ (text detector) มองไม่เห็นข้อความบริเวณใดเลย ข้อความบริเวณนั้นจะไม่ถูกส่งต่อไปยังขั้นตอนรู้จำตัวอักษรและ Fuzzy Matching เลย ไม่ว่าขั้นตอนหลังจากนั้นจะแม่นยำเพียงใดก็ไม่สามารถกู้คืนชื่อสารที่ตรวจจับไม่พบตั้งแต่ต้นได้ ในทางตรงข้าม หากตรวจพบกรอบข้อความแล้วแต่รู้จำตัวอักษรผิด ยังมีโอกาสที่ Fuzzy Matching จะแก้ไขให้ถูกต้องได้ ดังนั้น Recall ของการตรวจจับจึงเป็น "เพดาน" บนของความแม่นยำโดยรวมที่ขั้นตอนถัดไปไม่สามารถแก้ไขให้เกินได้ การวิเคราะห์ในหัวข้อ 4.1 ที่พบว่า Precision อยู่ระดับใกล้เคียงกับ Recall แต่ยังมีช่องว่างให้ปรับปรุงอีกมากในภาพรวม จึงชี้ให้เห็นว่าการเพิ่ม Recall ของการตรวจจับข้อความเป็นจุดที่ควรแก้ไขก่อนพารามิเตอร์ส่วนอื่น

### 4.2.1 ผล Sweep เบื้องต้น (n=40, "original")

ในหัวข้อนี้ **n=40** หมายถึงจำนวนภาพฉลากต้นฉบับ 40 ภาพที่ใช้เป็นชุดพัฒนาสำหรับการทดลองเปรียบเทียบค่าพารามิเตอร์เบื้องต้น ภาพทั้ง 40 ภาพถูกประมวลผลด้วยทุกค่า config ในตาราง เพื่อให้เปรียบเทียบผลของแต่ละค่าบนภาพชุดเดียวกันได้โดยตรง

| Config | Precision | Recall | Set F1 |
|---|---|---|---|
| Baseline (box_thresh=0.45) | 0.579 | 0.581 | 0.563 |
| **box_thresh=0.30** | 0.565 | **0.632** | **0.592** |
| box_thresh=0.30 + unclip_ratio=1.8 | 0.514 | 0.560 | 0.530 |
| unclip_ratio=1.8 (เดี่ยว) | 0.525 | 0.528 | 0.512 |
| limit_side_len=1536 | 0.425 | 0.426 | 0.409 |

การลด `box_thresh` เพียงอย่างเดียวให้ผลดีที่สุด สอดคล้องกับสมมติฐานว่าคอขวดคือ Recall ของการตรวจจับ ส่วนการเพิ่ม `unclip_ratio` หรือ `limit_side_len` กลับให้ผลแย่กว่า baseline ทั้งคู่

ทิศทางของผลกระทบจากค่า box_thresh สามารถอธิบายได้จากตารางข้างต้นเอง: ค่า box_thresh ที่**สูงกว่า 0.30** เช่นค่าเริ่มต้น 0.45 ในแถว Baseline หมายถึงเกณฑ์ที่**เข้มงวดกว่า** โมดูลตรวจจับจะทิ้งกรอบข้อความที่มีคะแนนความเชื่อมั่นต่ำกว่าเกณฑ์นี้ไปมากขึ้น ทำให้ได้ Recall ต่ำลง เนื่องจากกรอบข้อความจริงบางส่วนที่คะแนนไม่ถึงเกณฑ์ถูกทิ้งไปด้วย แต่ได้ Precision สูงขึ้นเล็กน้อย เพราะกรอบที่เหลือมักเป็นข้อความจริงที่ชัดเจน ดังที่เห็นได้จากแถว Baseline ที่มี Precision 0.579 สูงกว่าแถว box_thresh=0.30 ที่ 0.565 เล็กน้อย แต่ Recall ต่ำกว่าอย่างชัดเจนคือ 0.581 เทียบกับ 0.632 เมื่อรวมเป็น Set F1 แล้ว การลดค่า box_thresh ลงมาที่ 0.30 จึงให้ผลรวมที่ดีกว่า เพราะการเพิ่ม Recall ที่ได้มีน้ำหนักมากกว่า Precision ที่เสียไปเล็กน้อย ส่วนการลดค่าต่ำกว่า 0.30 ต่อไปอีกไม่ให้ประโยชน์เพิ่มเติม ดังแสดงในหัวข้อ 4.2.2

### 4.2.2 การหาจุด Plateau ของ box_thresh

ทดสอบ `box_thresh` เพิ่มเติมที่ 0.25, 0.20, 0.15 บนตัวอย่างชุดเดียวกัน (n=40) พบว่าทั้งสามค่าให้ผลลัพธ์ **เหมือนกับ box_thresh=0.30 ทุกประการ** เมื่อตรวจสอบระดับข้อความ OCR รายภาพ พบว่า raw text เหมือนกันทุกตัวอักษร แสดงว่ากรอบข้อความที่กู้คืนได้ด้วยการลด threshold ถูกกู้คืนหมดแล้วที่ 0.30 — ข้อความที่ยังพลาดอยู่หลังจากนี้คือกรณีที่โมดูลตรวจจับ "มองไม่เห็น" จริง ๆ ไม่ใช่แค่ถูกกรองทิ้งด้วย threshold **จึงสรุปว่า 0.30 คือค่าที่เหมาะสมที่สุดสำหรับพารามิเตอร์นี้ ไม่มีประโยชน์เพิ่มเติมจากการลดต่ำกว่านี้**

ในทางกลับกัน หากตั้งค่า `box_thresh` **สูงกว่า 0.30** เกณฑ์การรับกรอบข้อความจะเข้มงวดขึ้น กรอบข้อความจริงที่มีคะแนนความเชื่อมั่นต่ำบางส่วนจะถูกตัดทิ้ง ทำให้ Recall ลดลง แม้อาจช่วยให้ Precision สูงขึ้นเล็กน้อย ตัวอย่างเช่น ที่ค่า 0.45 Precision เท่ากับ 0.579 สูงกว่าค่า 0.30 ซึ่งเท่ากับ 0.565 แต่ Recall ลดจาก 0.632 เหลือ 0.581 และ Set F1 ลดจาก 0.592 เหลือ 0.563 ดังนั้น สำหรับชุดพัฒนา 40 ภาพนี้ ค่าเหนือ 0.30 ไม่ได้ให้ผลรวมที่ดีกว่า

### 4.2.3 ผลการ Validate เต็มรูปแบบ (n=216, "original")

| ตัวชี้วัด | box_thresh=0.45 (ก่อนปรับ) | box_thresh=0.30 (ปัจจุบัน) |
|---|---|---|
| mean CER (fuzzy) [95% CI] | 0.3199 [0.2781, 0.3626] | **0.2644** [0.2304, 0.2998] |
| mean IER | 0.6709 | 0.6757 |
| mean Set Precision | 0.5604 | 0.5487 |
| mean Set Recall | 0.5780 | **0.6127** |
| **mean Set F1** [95% CI] | 0.5515 [0.5114, 0.5917] | **0.5715** [0.5333, 0.6089] |

ผลยืนยันบนภาพเต็มสอดคล้องกับ sweep ตัวอย่างย่อย: Set F1 ดีขึ้นจาก 0.5515 เป็น 0.5715 (+3.6%) และ CER ดีขึ้นชัดเจนกว่า คือลดลง 17% โดยแลกกับ Precision ที่ลดลงเล็กน้อย เป็นการปรับปรุงที่ไม่ต้องใช้ข้อมูลหรือการฝึกโมเดลเพิ่มเติมเลย ค่า box_thresh = 0.30 นี้จึงถูกกำหนดเป็นค่าเริ่มต้นถาวรของระบบตั้งแต่นั้นเป็นต้นมา

ช่วง CI ที่แสดงในตารางเป็น CI รายเงื่อนไขเพื่อบรรยายความไม่แน่นอนของแต่ละค่าเท่านั้น ไม่ใช้ตัดสินความแตกต่างระหว่าง config เนื่องจากเป็นการเปรียบเทียบบนภาพชุดเดียวกัน จึงใช้ **paired bootstrap** วิเคราะห์ผลต่างโดยตรงเป็นผลหลัก ได้ผลต่าง mean Set F1 เท่ากับ **+0.0200** ที่ 95% CI [+0.0088, +0.0331] ซึ่งไม่ครอบคลุม 0 และผลต่าง mean CER เท่ากับ **−0.0555** ที่ 95% CI [−0.0741, −0.0392] ซึ่งไม่ครอบคลุม 0 เช่นกัน ผลนี้สนับสนุนว่าการปรับ `box_thresh` ให้ผลดีขึ้นภายในชุดข้อมูลที่ศึกษา รายละเอียดวิธีคำนวณอยู่ในหัวข้อ 3.10.4

### 4.2.4 การตรวจสอบผลบนภาพที่ไม่ใช้ในการ Sweep

การ sweep เบื้องต้นตามหัวข้อ 4.2.1-4.2.2 ใช้ภาพ 40 ภาพแรกที่เรียงตามชื่อไฟล์จากชุดข้อมูล "original" ในการหาค่า `box_thresh` ที่ดีที่สุด ก่อนนำค่านั้นไป validate เต็มรูปแบบบนภาพทั้ง 216 ภาพ ซึ่งรวม 40 ภาพที่ใช้ tune อยู่ด้วย จึงคำนวณ Set F1 แยกเฉพาะภาพ 176 ภาพที่ไม่ถูกใช้ในขั้นตอน sweep เพื่อดูว่าผลยังคงอยู่กับภาพส่วนที่ไม่ได้มีส่วนในการเลือกพารามิเตอร์หรือไม่ ในหัวข้อนี้เรียกว่า **ภาพชุดกันไว้ทดสอบ (held-out set)** ในความหมายที่กันไว้เฉพาะจากการ sweep ค่า `box_thresh` มิใช่ชุดทดสอบอิสระของ pipeline ทั้งหมด:

| กลุ่มภาพ | n | mean CER | mean Set F1 |
|---|---|---|---|
| ภาพทั้งหมด (ตัวเลขที่รายงาน) | 216 | 0.2644 | 0.5715 |
| เฉพาะ 40 ภาพที่ใช้ tune พารามิเตอร์ | 40 | 0.2616 | 0.5920 |
| **เฉพาะ 176 ภาพชุดกันไว้ทดสอบ (ไม่เคยใช้ tune)** | 176 | **0.2650** | **0.5669** |

ค่า Set F1 บนภาพชุดกันไว้ทดสอบ (0.5669) ต่างจากค่าที่รายงานบนภาพทั้งหมด (0.5715) เพียง 0.8% จึงเป็นหลักฐานสนับสนุนเบื้องต้นว่าผลของ `box_thresh=0.30` ไม่ได้จำกัดอยู่เฉพาะภาพ 40 ภาพที่ใช้ sweep อย่างไรก็ตาม การแบ่งนี้เกิดขึ้นภายหลังและภาพ 40 ภาพแรกไม่ได้สุ่มเลือก จึงไม่ทดแทนชุดทดสอบอิสระที่กำหนดไว้ล่วงหน้า

### 4.2.5 การตรวจสอบเสถียรภาพเพิ่มเติมด้วย k-fold Cross-validation

การตรวจสอบด้วยภาพชุดกันไว้ทดสอบในหัวข้อ 4.2.4 เป็นการแบ่งข้อมูลเพียงครั้งเดียว (single split) ซึ่งผลลัพธ์อาจขึ้นกับว่าภาพ 40 ภาพแรกที่ใช้ tune บังเอิญเป็นภาพกลุ่มใด เพื่อยืนยันความเสถียรของการเลือกพารามิเตอร์ด้วยวิธีที่เป็นมาตรฐานกว่า จึงทำ **5-fold cross-validation** เพิ่มเติมบนภาพชุดพัฒนา 40 ภาพเดิม (ซึ่งเป็นภาพชุดเดียวที่มีผลลัพธ์รายภาพครบทั้งค่า box_thresh=0.45 และ 0.30 สำหรับใช้เปรียบเทียบ) โดยแบ่งภาพออกเป็น 5 กลุ่มกลุ่มละ 8 ภาพ แต่ละรอบใช้ 4 กลุ่มเป็นข้อมูลฝึกเพื่อเลือกว่า box_thresh=0.45 หรือ 0.30 ให้ mean Set F1 สูงกว่า แล้ววัดผลของค่าที่เลือกบนกลุ่มที่เหลือซึ่งไม่ได้มีส่วนในการเลือกเลย ทำซ้ำจนครบ 5 รอบ สคริปต์ที่ใช้คำนวณคือ `compute_kfold_check.py` ระบุไว้ในภาคผนวก ก

ผลปรากฏว่า **box_thresh=0.30 ถูกเลือกในข้อมูลฝึกครบทั้ง 5 รอบ** โดยไม่มีรอบใดที่ box_thresh=0.45 ให้ mean Set F1 สูงกว่าบนข้อมูลฝึก และเมื่อวัดผลของค่าที่เลือกบนข้อมูล test ของแต่ละรอบ ได้ mean Set F1 เฉลี่ยทั้ง 5 รอบเท่ากับ 0.5920 โดยมีส่วนเบี่ยงเบนมาตรฐานระหว่างรอบ 0.0929 ผลนี้สนับสนุนว่าการเลือก `box_thresh=0.30` มีความสม่ำเสมอภายในชุดพัฒนา 40 ภาพ อย่างไรก็ตาม เป็นการตรวจสอบย้อนหลังบนผลลัพธ์ที่มีอยู่แล้วของภาพ 40 ภาพแรก และพิจารณาเพียงสองค่า คือ 0.45 และ 0.30 จึงไม่ใช่การประเมินประสิทธิภาพของ pipeline แบบอิสระ ผลลัพธ์หลักจึงควรตีความร่วมกับข้อจำกัดเรื่องการแบ่งชุดข้อมูลในหัวข้อ 5.2

## 4.3 คอขวดที่เหลืออยู่: Recall จากการตรวจจับข้อความ

จากการวิเคราะห์เชิงคุณภาพพบว่าประมาณ **62.7%** ของชื่อสารที่ระบบพลาดไม่ใช่เพราะแก้ไขข้อความผิดพลาด แต่เป็นเพราะโมดูลตรวจจับข้อความ (text detector) ไม่พบกรอบข้อความบริเวณนั้นเลยตั้งแต่ต้น ซึ่งเป็นข้อจำกัดที่การปรับพารามิเตอร์ระดับ inference ในหัวข้อ 3.9 และ 4.2 แก้ไขได้เพียงบางส่วนเท่านั้น ดังข้อสรุปในหัวข้อ 4.2.2 งานต่อไปควรทดสอบการปรับปรุงคุณภาพหรือความละเอียดของภาพต้นทาง และการ fine-tune โมเดลตรวจจับข้อความให้เหมาะกับลักษณะฉลากเครื่องสำอางโดยเฉพาะ ซึ่งต้องใช้ข้อมูล bounding-box annotation เพิ่มเติมและทรัพยากร GPU สำหรับการฝึกโมเดล ทั้งนี้ โครงงานนี้ยังไม่มีหลักฐานทดลองเพียงพอที่จะสรุปว่าแนวทางใดจะแก้คอขวดดังกล่าวได้ดีที่สุด

### 4.3.1 การทดสอบ Upscaling ภาพต้นทางร่วมกับ Pipeline ปัจจุบัน

เนื่องจากภาพในชุดข้อมูลมีความสูงมัธยฐานเพียง 170.5 พิกเซล จึงตั้งสมมติฐานว่าการขยายภาพ (upscaling) ก่อนเข้าสู่ขั้นตอนตรวจจับข้อความอาจช่วยเพิ่ม Recall ได้ การทดลอง upscale ที่เคยทำไว้ก่อนหน้านี้ถูกรันก่อนการแก้ไข engine configuration หลักในหัวข้อ 3.5 (การแก้บัค mkldnn, การเปิด document unwarping/textline orientation, การปรับ box_thresh) จึงไม่สามารถใช้เปรียบเทียบกับ pipeline ปัจจุบันได้อย่างเป็นธรรม จึงทดสอบซ้ำโดยนำเทคนิค upscale เดิม คือการขยายภาพที่สูงต่ำกว่า 480 พิกเซลให้ถึง 480 พิกเซลด้วยวิธี cubic interpolation มาใช้ร่วมกับ pipeline ปัจจุบันทั้งหมด ทั้ง border padding, document unwarping, box_thresh=0.30 และ fuzzy matching บนภาพชุดพัฒนา 40 ภาพเดิมที่ใช้ tune พารามิเตอร์ตามหัวข้อ 4.2.4 เพื่อเทียบกับ baseline ตรงๆ:

| Config (n=40) | Precision | Recall | Set F1 | CER |
|---|---|---|---|---|
| Pipeline ปัจจุบัน (ไม่ upscale) | 0.5650 | **0.6324** | **0.5920** | **0.2616** |
| Pipeline ปัจจุบัน + upscale (cubic, target 480px) | 0.5334 | 0.5655 | 0.5331 | 0.3418 |

ผลปรากฏว่า upscale ทำให้แย่ลงทั้ง Precision และ Recall แม้จะใช้ร่วมกับ engine configuration ที่แก้ไขแล้วก็ตาม โดย Precision ลดลงจาก 0.5650 เหลือ 0.5334 คือลดลง 0.0316 จุด หรือประมาณ 5.6% และ Recall ลดลงจาก 0.6324 เหลือ 0.5655 คือลดลง 0.0669 จุด หรือประมาณ 10.6% ส่งผลให้ Set F1 ลดลงจาก 0.5920 เหลือ 0.5331 คือลดลง 0.0589 จุด หรือประมาณ 9.9% และ CER แย่ลงจาก 0.2616 เป็น 0.3418 สันนิษฐานว่า cubic interpolation สร้าง artifact หรือความเบลอที่ส่งผลเสียต่อขั้นตอนรู้จำตัวอักษรมากกว่าประโยชน์ที่ได้จากการช่วยให้ตัวตรวจจับเห็นข้อความชัดขึ้น

ผลการทดลองนี้แสดงเพียงว่า cubic interpolation แบบง่ายไม่ได้ช่วยแก้ปัญหา Recall ในกรณีนี้ และตอกย้ำข้อสรุปหลักของโครงงานในหัวข้อ 4.6 ว่าเทคนิค preprocessing เชิงภาพที่ทดลองยังไม่ให้ประโยชน์เพิ่มเมื่อใช้ร่วมกับ pipeline ที่ปรับ configuration แล้ว ผลดังกล่าวไม่ใช่หลักฐานว่า fine-tune โมเดลตรวจจับข้อความจะแก้คอขวด Recall ได้จริง จึงควรถือการ fine-tune เป็นข้อเสนอสำหรับการทดลองในอนาคต ไม่ใช่ข้อสรุปของโครงงานนี้

ผลที่ได้แบ่งชัดเจนเป็นสองกลุ่ม:

- **indoor และ low_light เสื่อมประสิทธิภาพแบบค่อยเป็นค่อยไป** (Set F1 ลดจาก 0.57 เหลือ 0.53 และ 0.46 ตามลำดับ) สอดคล้องกับสมมติฐานว่าแสงน้อย/สีเพี้ยนระดับปานกลางไม่กระทบการตรวจจับข้อความรุนแรง เพราะทุกภาพยังตรวจพบข้อความได้อย่างน้อยบางส่วน (0% ภาพที่ตรวจจับไม่ได้เลย)
- **blur และ night เสื่อมประสิทธิภาพแบบฉับพลัน** — Set F1 ลดลงเหลือประมาณ 0.14 และ mean IER สูงเกือบ 1.0 ส่วนหนึ่งเกิดจากภาพ blur 10.2% และ night 13.4% ที่โมดูลตรวจจับข้อความไม่พบกรอบข้อความเลย แต่ความเสียหายส่วนใหญ่มาจากภาพที่ยังตรวจพบข้อความบางส่วนแต่รู้จำตัวอักษรผิดเพี้ยนมาก จึงสะท้อนว่าการเบลอหรือแสงน้อยมากกระทบทั้งการตรวจจับและการรู้จำข้อความ ไม่ใช่เฉพาะ Recall ของการตรวจจับดังที่พบในภาพ original

ข้อค้นพบนี้เป็นข้อควรระวังสำคัญต่อผลลัพธ์หลักของโครงงาน (Set F1 = 0.57 บนหัวข้อ 4.1-4.2): **ตัวเลขดังกล่าวใช้ได้กับภาพที่มีคุณภาพระดับ original/indoor/low_light เท่านั้น** หากนำไปใช้กับภาพที่ผู้ใช้ถ่ายในสภาพเบลอหรือแสงน้อยมาก (night) ความแม่นยำจะตกลงอย่างมีนัยสำคัญ ระบบในสถานะปัจจุบันจึงยังไม่พร้อมสำหรับภาพคุณภาพต่ำระดับนั้นโดยไม่มีขั้นตอนเสริม (เช่น การแจ้งเตือนผู้ใช้ให้ถ่ายภาพใหม่เมื่อภาพเบลอ/มืดเกินไป)

## 4.5 แผนต่อไป

**เป้าหมาย Set F1 ที่ 0.70** ยังไม่สามารถยืนยันได้จากการปรับพารามิเตอร์หรือ config tuning ที่ทดลองในโครงงานนี้ เนื่องจากพบคอขวด Recall จากการตรวจจับข้อความตามหัวข้อ 4.3 และผลการเสื่อมประสิทธิภาพในสภาพแวดล้อม blur/night ตามหัวข้อ 4.4 งานต่อไปควรทดลองแนวทาง เช่น การตรวจจับภาพเบลอหรือมืดเกินไปแล้วขอให้ผู้ใช้ถ่ายใหม่ การปรับปรุงคุณภาพภาพต้นทาง และการ fine-tune โมเดลตรวจจับหรือรู้จำข้อความเฉพาะทาง แล้วประเมินผลบนชุดทดสอบอิสระก่อนสรุปประสิทธิผล

นอกจากความแม่นยำแล้ว **เวลาประมวลผล** ก็เป็นข้อจำกัดที่ต้องพิจารณาก่อนนำไปใช้งานจริง: การรัน PP-OCRv6_medium บน CPU ใช้เวลาเฉลี่ย ~16 วินาที/ภาพตามหัวข้อ 3.5 ซึ่งช้าเกินกว่าจะใช้เป็น real-time feedback ให้ผู้ใช้ขณะถ่ายภาพในแอปพลิเคชันจริง งานพัฒนาต่อจึงควรพิจารณาการรันบน GPU ที่รองรับ เนื่องจากหัวข้อ 3.11 พบว่า GPU รุ่นที่ใช้พัฒนายังมีปัญหา compatibility กับ PaddlePaddle หรือออกแบบการประมวลผลแบบ asynchronous คือประมวลผลเบื้องหลังแล้วแจ้งผลภายหลัง ควบคู่ไปกับการพัฒนาความแม่นยำ

## 4.6 การอภิปรายผล

ผลการทดลองแสดงให้เห็นว่าการวินิจฉัยและแก้ไขการตั้งค่าของโมดูล OCR สำเร็จรูปอย่างเป็นระบบร่วมกับการปรับฐานคำศัพท์และ threshold ทำให้ Set F1 ขยับจาก 0.39 เป็น 0.57 ในชุดข้อมูลที่ศึกษา อย่างไรก็ตาม ผลนี้เป็นจริงเฉพาะภาพคุณภาพระดับ original, indoor และ low_light เท่านั้น (หัวข้อ 4.4)

ประเด็นสำคัญที่ควรเน้นในการอภิปราย:

1. **การตั้งค่าฟีเจอร์ในตัวของโมเดลผิดพลาดสร้างความเสียหายมากกว่าที่คาด** — การปิด document unwarping/textline orientation ซึ่งเดิมตั้งใจปิดเพื่อทดสอบ preprocessing แบบแยกส่วนอย่างเป็นธรรม กลับเป็นการเสียโอกาสความแม่นยำที่โมเดลมีอยู่แล้วโดยไม่จำเป็น
2. **การปรับพารามิเตอร์ inference ของโมดูลตรวจจับข้อความ (box_thresh) ให้ผลตอบแทนสูงเทียบกับต้นทุน** เพราะไม่ต้องมีข้อมูลหรือฝึกโมเดลเพิ่มเติมเลย แต่พบจุด plateau ในชุดข้อมูลนี้ที่ 0.30 การพัฒนาต่อควรทดลองแนวทางอื่น เช่น การปรับปรุงภาพต้นทางหรือการ fine-tune โดยยังไม่อาจสรุปได้ว่าแนวทางใดจะให้ผลดีที่สุด
3. **การเสริมฐานข้อมูลคำศัพท์ต้องคัดสรรอย่างระมัดระวัง** — ยิ่งใส่คำศัพท์มากไม่ได้แปลว่ายิ่งดีเสมอไป (การใส่แบบ "oracle" ทุกชื่อกลับทำให้แย่ลง) ควรคัดเฉพาะคำที่พบบ่อยจริงในข้อมูลเป้าหมาย
4. **คอขวดที่เหลืออยู่ (Recall จากการตรวจจับข้อความ) เป็นข้อจำกัดของ pipeline ที่ศึกษา** ซึ่งการปรับพารามิเตอร์ระดับ inference แก้ได้เพียงบางส่วน งานต่อไปจึงควรทดลองแนวทางอื่น เช่น การปรับปรุงคุณภาพภาพต้นทางหรือการ fine-tune โมเดลเฉพาะทาง แทนการค้นหาพารามิเตอร์เพิ่มเติมเพียงอย่างเดียว
5. **ความทนทานต่อสภาพแวดล้อม (environmental robustness) ไม่สม่ำเสมอ** — pipeline ที่ปรับแต่งจน Set F1 = 0.57 บนภาพคุณภาพปกติ กลับล้มเหลวแบบฉับพลัน (Set F1 ~0.14) บนภาพเบลอหรือแสงน้อยมาก ชี้ให้เห็นว่าความแม่นยำที่วัดได้บนชุดข้อมูล "original" ไม่ควรถูกอนุมานว่าใช้ได้กับภาพถ่ายจริงจากผู้ใช้ทุกสภาพ ระบบที่นำไปใช้งานจริงควรมีกลไกตรวจจับคุณภาพภาพก่อนเข้าสู่ OCR (blur/brightness detection) เพื่อขอให้ผู้ใช้ถ่ายใหม่ในกรณีที่คาดว่าจะได้ผลลัพธ์แย่
6. **ความแม่นยำระดับ Set F1 = 0.57 ยังไม่เพียงพอสำหรับการตัดสินใจอัตโนมัติเต็มรูปแบบในงานที่เกี่ยวข้องกับความปลอดภัยของผิว** — เนื่องจากเป้าหมายปลายทางของโครงงานคือระบบแนะนำสกินแคร์ที่ต้องอ้างอิงรายชื่อสารเพื่อประเมินความเสี่ยงต่อผู้ใช้ ความคลาดเคลื่อนที่ยังเหลืออยู่เกือบครึ่งหนึ่งของชื่อสารหมายความว่า**ไม่ควรนำผลจาก OCR ไปใช้ตัดสินใจ เช่น ฟันธงว่าปลอดภัยหรือไม่ปลอดภัย โดยอัตโนมัติทั้งหมด** ในขั้นพัฒนาต่อควรออกแบบให้มีขั้นตอนแสดงรายชื่อสารที่ระบบอ่านได้ให้ผู้ใช้ยืนยัน/แก้ไขก่อนนำไปประมวลผลต่อ (human-in-the-loop) แทนที่จะเชื่อผล OCR ทั้งหมดโดยไม่มีการตรวจสอบ

### ข้อสรุปภาพรวม

สำหรับชุดข้อมูลภาพฉลากส่วนผสมที่ crop มาเป็นแถบเล็กและมีความละเอียดต่ำ การวินิจฉัยและแก้ไขการตั้งค่า pipeline ของโมดูล OCR สำเร็จรูปอย่างเป็นระบบ ได้แก่ engine configuration, border padding, ฐานข้อมูลคำศัพท์ และ detection threshold ให้ผลดีกว่าเทคนิค preprocessing เชิงภาพที่ทดลองในโครงงานนี้ ผลลัพธ์ชี้ว่าควรตรวจสอบการตั้งค่าของโมดูลสำเร็จรูปให้เหมาะสมก่อนลงทุนพัฒนาเทคนิคเสริมที่ซับซ้อน Pipeline ปัจจุบันให้ค่า Set F1 = 0.57 และ CER = 0.26 บนภาพจริง 216 ภาพ แต่ผลดังกล่าวมีข้อจำกัดทั้งด้านการแบ่งชุดข้อมูลและภาพที่ใช้คัดเลือกคำศัพท์ การประเมินใน 5 สภาพแวดล้อมพบว่าผลลัพธ์ใช้ได้กับภาพระดับ original, indoor และ low_light เท่านั้น ส่วนภาพ blur และ night ให้ Set F1 ประมาณ 0.14 ดังนั้นการนำระบบไปใช้งานจริงควรเพิ่มกลไกตรวจสอบคุณภาพภาพก่อนเข้าสู่ OCR และควรประเมินแนวทางพัฒนาต่อบนชุดทดสอบอิสระ

# บทที่ 5 สรุปผลการวิจัยและข้อเสนอแนะ

## 5.1 สรุปผลการวิจัยตามวัตถุประสงค์

โครงงานนี้บรรลุวัตถุประสงค์ทั้ง 4 ข้อที่ตั้งไว้ในหัวข้อ 1.2 ดังนี้

1. **พัฒนาระบบ OCR สำหรับดึงข้อความส่วนผสมจากภาพฉลากเครื่องสำอาง** — ได้ระบบต้นแบบแบบ end-to-end ที่ทำงานได้จริงตามลำดับ รับภาพ → เพิ่มขอบภาพ → ดึงข้อความด้วย OCR → จับคู่ชื่อสารด้วย Fuzzy Matching → รายชื่อส่วนผสม (หัวข้อ 3.2) ผ่านการทดสอบบนภาพจริง 216 ภาพ และภาพจำลองสภาพแวดล้อมอีก 864 ภาพ รวม 1,080 ภาพ
2. **วินิจฉัยและแก้ไขการตั้งค่า pipeline ของ PaddleOCR** — พบและแก้ไขจุดตั้งค่าผิดพลาด 4 จุด ได้แก่ บัค mkldnn, engine feature flag ที่ถูกปิดผิด, ช่องโหว่ฐานข้อมูลคำศัพท์ และบัค post-processing ทำให้ Set F1 เพิ่มจาก 0.39 เป็น 0.55 และการปรับ detection box threshold เพิ่มเติมจาก 0.45 เป็น 0.30 ทำให้เพิ่มเป็น 0.57 โดยผลต่างของการปรับ threshold ได้รับการประเมินด้วย paired bootstrap ตามหัวข้อ 4.2
3. **พัฒนากระบวนการตรวจจับชื่อสารด้วย Fuzzy String Matching ร่วมกับฐานข้อมูล INCI ที่เสริมคำศัพท์** — เสริมฐานข้อมูลหลัก 11,091 รายการด้วยคำศัพท์คัดสรร 199 รายการ รวมเป็น 11,290 รายการ พร้อมพบข้อสังเกตสำคัญว่าการเสริมคำศัพท์ต้องคัดสรรอย่างระมัดระวัง ไม่ใช่ยิ่งใส่มากยิ่งดี ดังอธิบายในหัวข้อ 3.7
4. **ประเมินประสิทธิภาพด้วยตัวชี้วัดระดับชื่อสารร่วมกับ CER/WER** — วางกรอบการประเมินผลที่ครบถ้วน ทั้ง Set Precision/Recall/F1, IER, CER, WER พร้อม 95% Bootstrap CI และนำไปใช้ validate ทั้งภาพจริงและภาพจำลองสภาพแวดล้อมครบทั้ง 5 แบบตามหัวข้อ 3.10 และ 4.4

โดยสรุป Pipeline ที่ผ่านการวินิจฉัยและปรับแต่งแล้วให้ค่า **Set F1 = 0.57 และ CER = 0.26** บนภาพฉลากเครื่องสำอางจริงคุณภาพปกติถึงแสงน้อยปานกลาง ซึ่งดีขึ้นจาก pipeline ตั้งต้นที่มีปัญหาการตั้งค่าถึง 46% โดยอาศัยเพียงการแก้ไขการตั้งค่าของโมดูลสำเร็จรูปที่มีอยู่แล้ว ไม่ต้องฝึกโมเดลใหม่หรือเพิ่มเทคนิค preprocessing เชิงภาพที่ซับซ้อน สนับสนุนสมมติฐานหลักของโครงงานที่ว่าการวินิจฉัยการตั้งค่าอย่างเป็นระบบเป็นแนวทางที่คุ้มค่ากว่าการทดลอง preprocessing แบบลองผิดลองถูก

## 5.2 ข้อจำกัดของงานวิจัย

1. **ความแม่นยำยังไม่สม่ำเสมอในทุกสภาพแวดล้อม** — ระบบล้มเหลวแบบฉับพลันบนภาพเบลอและภาพแสงน้อยมาก (Set F1 ~0.14) จึงยังไม่สามารถรับประกันคุณภาพผลลัพธ์ได้หากไม่ทราบสภาพการถ่ายภาพล่วงหน้า (หัวข้อ 4.4)
2. **คอขวด Recall ของการตรวจจับข้อความยังไม่ได้รับการแก้ไขที่ต้นตอ** — ประมาณ 62.7% ของชื่อสารที่พลาดเกิดจากโมดูลตรวจจับมองไม่เห็นข้อความตั้งแต่ต้น ซึ่งการปรับพารามิเตอร์ระดับ inference แก้ได้เพียงบางส่วนและถึงจุด plateau แล้วที่ box_thresh = 0.30 (หัวข้อ 4.2.2, 4.3)
3. **เวลาประมวลผลยังช้าเกินสำหรับการใช้งานแบบ real-time** — เฉลี่ย ~16 วินาที/ภาพบน CPU เนื่องจากข้อจำกัดความเข้ากันได้ของ GPU ที่ใช้พัฒนากับ PaddlePaddle (หัวข้อ 3.11, 4.5)
4. **ขอบเขตจำกัดเฉพาะส่วน backend ของ pipeline** — ยังไม่รวมส่วนติดต่อผู้ใช้ (UI/mobile app) หรือ API สำหรับผนวกเข้ากับระบบแนะนำสกินแคร์ตัวจริง (หัวข้อ 1.3)
5. **การแบ่งชุดข้อมูล tuning/test ไม่ได้แยกจากกันตั้งแต่ต้นตามหลักทฤษฎีมาตรฐาน** การตรวจสอบย้อนหลังทั้งด้วยภาพชุดกันไว้ทดสอบและ 5-fold cross-validation ช่วยสนับสนุนความสม่ำเสมอของการเลือก `box_thresh` แต่ไม่ทดแทนการประเมินบนชุดทดสอบอิสระที่กำหนดไว้ล่วงหน้า (หัวข้อ 4.2.4, 4.2.5)
6. **การสร้าง vocabulary patch ใช้ Ground Truth จากภาพชุดเดียวกับที่ใช้รายงานผล** จึงเป็นการปรับฐานคำศัพท์เชิงสำรวจและอาจทำให้ผลหลังเสริมคำศัพท์สูงกว่าที่จะพบในข้อมูลใหม่ งานต่อไปควรคัดเลือกคำศัพท์จากชุดพัฒนาและประเมินบนชุดทดสอบแยกต่างหาก (หัวข้อ 3.7)

## 5.3 ข้อเสนอแนะสำหรับการพัฒนาต่อ

1. **เพิ่มกลไกตรวจสอบคุณภาพภาพก่อนเข้าสู่ OCR** ทั้ง blur detection และ brightness detection เพื่อแจ้งเตือนให้ผู้ใช้ถ่ายภาพใหม่ก่อนที่จะได้ผลลัพธ์ที่ผิดพลาดโดยไม่รู้ตัว โดยเฉพาะในสภาพเบลอหรือแสงน้อยมาก
2. **ทดสอบการ fine-tune โมเดลตรวจจับข้อความสำหรับฉลากเครื่องสำอาง** โดยเตรียมข้อมูล bounding-box annotation และทรัพยากร GPU เพิ่มเติม แล้วเปรียบเทียบกับ pipeline ปัจจุบันบนชุดทดสอบอิสระ เพื่อประเมินว่าช่วยเพิ่ม Recall ได้จริงหรือไม่
3. **ปรับปรุงประสิทธิภาพด้านเวลาประมวลผล** ด้วยการรันบน GPU ที่รองรับ หรือออกแบบการประมวลผลแบบ asynchronous เพื่อให้ใช้งานได้จริงในแอปพลิเคชัน
4. **ออกแบบขั้นตอน human-in-the-loop** ให้ผู้ใช้ยืนยัน/แก้ไขรายชื่อสารที่ระบบอ่านได้ก่อนนำไปประมวลผลต่อในระบบแนะนำสกินแคร์ แทนการเชื่อผล OCR ทั้งหมดโดยอัตโนมัติ เนื่องจากความแม่นยำปัจจุบันยังไม่เพียงพอสำหรับการตัดสินใจที่เกี่ยวข้องกับความปลอดภัยของผิว
5. **พัฒนาส่วนติดต่อผู้ใช้และ API** เพื่อผนวกโมดูล OCR ที่ผ่านการวินิจฉัยและปรับแต่งแล้วเข้ากับระบบแนะนำสกินแคร์ที่เหมาะสมกับผู้ใช้ตามเป้าหมายปลายทางของโครงงาน (หัวข้อ 1.4)

## ภาคผนวก ข: การตั้งค่า PaddleOCR ฉบับเต็มที่ใช้จริง

```python
PaddleOCR(
    lang="en",
    use_doc_orientation_classify=False,
    use_doc_unwarping=True,        # เปิด: ลด mean CER เทียบกับปิด (validated, หัวข้อ 3.5)
    use_textline_orientation=True, # เปิด: ลด mean CER เทียบกับปิด (validated, หัวข้อ 3.5)
    device="cpu",                  # เหตุผลด้าน hardware compatibility ในหัวข้อ 3.11
    enable_mkldnn=False,           # ปิด: หลีกเลี่ยงบัค crash ("ConvertPirAttribute2RuntimeAttribute not support ...")
    text_det_box_thresh=0.30,      # ลดจาก default 0.45 — เพิ่ม Recall การตรวจจับข้อความ (หัวข้อ 3.9, 4.2)
)
```

พารามิเตอร์ Fuzzy Matching (RapidFuzz): `scorer=fuzz.ratio`, `score_cutoff=90`, เงื่อนไขอัตราส่วนความยาวตัวอักษรระหว่าง token กับชื่อที่จับคู่ได้ไม่เกิน 1.6 เท่า (หัวข้อ 3.8)

Border Padding: `pad_px = round(min(height, width) × 0.25)` ผ่าน `cv2.copyMakeBorder` (หัวข้อ 3.6)
